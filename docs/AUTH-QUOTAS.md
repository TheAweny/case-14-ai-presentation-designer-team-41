# Доступ и опциональные ограничения

Актуальная политика заменяет денежный enforcement из раннего плана восстановления генерации.
Миграция `024_enterprise_access.sql` не создаёт ни одного ограничения. Аккаунт без политики
работает без индивидуальных квот; внутренние технические пределы действуют всегда.

## Политика

Источник контрактов — `packages/contracts/src/account-policy.ts`. Общая политика хранится
в `account_policies.scope='default'`, индивидуальная — под ID аккаунта.

| Значение поля                  | Действие                                          |
| ------------------------------ | ------------------------------------------------- |
| Поле отсутствует               | Наследовать только явно установленный общий лимит |
| `null`                         | Без ограничения, включая отмену общего лимита     |
| `{limit: 0, ...}`              | Явный запрет новых операций этого вида            |
| `{limit: N, period, timezone}` | Независимый включённый лимит                      |

Период — `lifetime`, календарный `day` или `month` в явно выбранной IANA timezone.
Границы и события хранятся UTC; интерфейс показывает сброс в timezone политики.
Concurrency и storage не имеют периодического сброса. Изменения политики не удаляют историю;
повторное включение учитывает сохранённую активность текущего окна. Снижение лимита
останавливает новые допуски, а уже допущенная операция может завершиться.
Администраторы подчиняются тем же лимитам при выполнении своих операций.

## Каталог активности

| Метрика              | Одна операция и точка завершения                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| `generation`         | Устойчивый generation build ID; успех после всех запрошенных вариантов и обязательных файлов                 |
| `assistant-response` | Принятый ход чата с request ID; успех в транзакции сохранения финального сообщения ассистента                |
| `edit`               | Подтверждённая редакция редактора с idempotency key; успех в транзакции snapshot и результата сохранения     |
| `image`              | Зарезервированная категория самостоятельной генерации изображения; отдельного публичного маршрута сейчас нет |
| `concurrency`        | Активная сборка, включая все её варианты, занимает один слот                                                 |
| `storage`            | Сохраняемые пользовательские файлы и JSON редактора, в байтах                                                |

Планирование, подготовка шаблона, tools, model calls, ремонты, retries, проверка моделей
и изображения внутри колоды не создают самостоятельных продуктовых операций.
Утверждение плана в чате запускает generation и не расходует дополнительный assistant-response.
Обычный ответ ассистента с инструментами учитывается один раз как ответ.
Каждая подтверждённая autosave-редакция — отдельный `edit`; конфликт или отказ не является успехом.
Полное regenerate использует новый request/build ID; resume и duplicate start сохраняют старый.
Частичная готовность, failure и cancel не расходуют generation success; готовые файлы сохраняются.
Скачивание и повторный экспорт существующей редакции не являются новой генерацией.

## Атомарность и восстановление

`AccountUsageStore` сериализует допуски аккаунта транзакционной PostgreSQL advisory lock.
Перед стартом проверяется `completed + active` в выбранном окне. Резерв сохраняется независимо
от наличия включённого лимита; это позволяет включить лимит без сброса истории.
Период операции определяется допуском. Освобождённый resume получает резерв нового периода
под прежним operation ID. Завершённая операция повторно не списывается.

Generation success и освобождение резерва записываются вместе с terminal build state.
Для чата и редактора SQL triggers завершают операцию вместе с сообщением или idempotency outcome.
Падение callback после commit не теряет учёт; состояние `done` только в памяти не считается успехом.
Generation reconcile проверяет build state и lease, чат — истечение heartbeat и отсутствие
живой session advisory lock. Правка редактора держит отдельную session advisory lock от
допуска до завершения, включая очередь storage и подсчёт байтов до начала snapshot-транзакции.
Reconcile освобождает просроченный edit только после потери этой блокировки и блокировки
транзакции колоды. Перед записью snapshot проверяется worker ID с блокировкой строки
операции: старый worker не может сохранить редакцию после потери допуска.
Допуск, storage и cleanup используют одно удерживаемое соединение, чтобы ожидающие записи
не исчерпывали pool, необходимый для завершения текущей записи.
SSE disconnect не освобождает резерв. Запрос resume сохраняет checkpoints и fencing сборки.

## Хранение и подключённые пути

`AccountUsageService.write` держит account storage lock на время резерва, записи и сверки.
Reservation хранится в PostgreSQL до завершения. Следующий владелец той же блокировки
восстанавливает orphan reservations; истечение времени само по себе не разрешает второго writer.

Подключены upload шаблонов и материалов, публикация вариантов генерации, media редактора,
сохранение snapshots/conflicts/idempotency, экспорт сохранённой редакции и legacy edited export.
Autosave сохраняет прежний протокол revisions/conflicts. Дополнительный callback проверяет
реальный размер внутри транзакции до commit; отказ сохраняет последнюю подтверждённую редакцию.
Повтор уже сохранённого idempotency key возвращает прежний результат без нового допуска.

Существующие uploads и опубликованные run directories измеряются на диске; editor JSON —
через `pg_column_size`. Media aliases с одним storage key учитываются один раз в пределах
аккаунта и колоды; revisions содержат ссылки и не копируют байты. Между колодами media
физически раздельны и учитываются раздельно. Общий шаблон учитывается у загрузившего его
аккаунта, а не у каждого читателя. Технические execution directories, checkpoints, индекс
подготовки и сообщения чата не входят в продуктовую storage-метрику; для них нужны общие
инфраструктурные пределы диска и retention.

Для JSON/upload известный размер резервируется консервативно. Размер render/export заранее
неизвестен: резервируется оставшийся объём, запись проходит в отдельном каталоге, превышение
удаляется до выдачи export ID. Это ограничение опубликованного хранения; временный рендер
может потребовать больше места на диске. Последняя редакция и готовые файлы остаются доступны.
Storage lock и файловый каталог должны быть общими для реплик, как и PostgreSQL.

## Сессии и границы доступа

Аккаунты по-прежнему создаёт администратор. При входе выдаётся случайный 256-bit session token;
PostgreSQL хранит только SHA-256, владельца, срок и отзыв. Подписанная HttpOnly/SameSite=Lax
cookie содержит ID и token. Старые cookies без серверной сессии требуют повторного входа.
В production Secure включён по умолчанию; для осознанного локального HTTP есть
`SESSION_COOKIE_SECURE=false`. За TLS-прокси задайте `APP_ORIGIN` точным публичным origin.
Произвольные forwarded host/proto/IP не дают доверия origin или нового окна login rate limit.

Logout отзывает текущий token на сервере, затем удаляет cookie. Смена/сброс пароля, роль и
блокировка отзывают все старые tokens транзакционным trigger. Явный отзыв администратором
тоже серверный и аудируемый. Новая сессия при входе проверяет пароль повторно под блокировкой
аккаунта, чтобы reset между проверкой и выдачей не оставлял действительный старый доступ.

Каждый API boundary требует service token и проверенную сессию с совпадающим владельцем;
один `x-lct-user` недостаточен. Каждый server action обращается к `requireAccount`.
`/api/service-status` также использует серверную проверку сессии и передаёт только ID аккаунта,
а не весь payload cookie; отзыв сессии закрывает и этот маршрут.
Мутации browser backend proxy требуют доверенный Origin. Next server actions дополнительно
проверяют Origin средствами Next. Service token и session bearer не передаются клиентскому UI.
Login throttling — 20 попыток на нормализованную почту и 200 на установку за 15 минут,
до bcrypt; forwarded IP не используется. Перед каждым новым физическим model send
проверяется блокировка аккаунта; выполненные результаты сохраняются.

Изменения policy записывают actor/before/after в `account_policy_audit`; изменения аккаунта
аудируются атомарно с обновлением, reset отмечается флагом без пароля/hash. Admin revoke
пишет отдельное событие. Защита ownership существующих проектов, шаблонов, чатов,
редакций/media/exports и model connections остаётся на API, включая direct requests.

## Ledger и ошибки

`provider_attempts` хранит физические вызовы, токены, время, ошибки и доступную стоимость.
Добавлены connection ID и scope `personal/shared/server`. Переключение подключения не меняет
account operation ID и не обходит policy; автоматического fallback на чужой ключ нет.
Нет пользовательского денежного баланса, paywall или обязательного тарифа.
Legacy `budget.maxCost/currency` принимаются для совместимости, денежный enforcement снят.
Неизвестная цена остаётся неизвестной, а не нулевой, и не блокирует выполнение.

Сохраняются deadlines, bounded retries, входные ограничения, provider Retry-After,
лимиты запросов/токенов сборки и внутренние account caps non-build вызовов за последний час
(10 000 запросов / 100 000 000 токенов). Это технические потолки, не тарифные квоты аккаунта.
`account-limit` с метрикой и временем сброса возвращает 403 и отличается от provider 429.
Текущий limiter RPM/TPM остаётся процессным; он не заявляется глобальным provider scheduler.

## Проверка и эксплуатация

Миграции применяет существующий `PostgresRunRepository.migrate` при старте API. Делайте backup
PostgreSQL и runs перед обновлением. На первом входе после миграции пользователи авторизуются
повторно. Не включайте политику при миграции; администратор делает это явно в настройках.
Для production нужны HTTPS, общий filesystem для реплик и установленный service token.

```powershell
$env:NX_DAEMON='false'
$env:NX_ISOLATE_PLUGINS='false'
$env:RUN_STORE_TEST_DATABASE_URL='postgresql://recovery:recovery-local@127.0.0.1:55419/recovery'
yarn nx run-many '--targets=typecheck,lint' '--projects=contracts,run-store,pipeline,api,web' --parallel=3
yarn nx run-many --targets=test '--projects=contracts,run-store,pipeline,api,web' --parallel=2 --maxWorkers=4
```

PostgreSQL tests используют отдельные схемы: cross-replica admission, failure/resume, inheritance,
периоды/DST, безлимитный default, lifecycle счётчиков, copied sessions, reset/disable,
forged headers, login throttle, storage concurrency, dedup и отказ snapshot до commit.
Browser fixture `account-policy.e2e.ts` проверяет сохранение лимита и logout скопированной cookie;
`recovery.e2e.ts` — новую сессию, восстановление редакции и export без модели, при
`RECOVERY_ACCESS=1` — с включёнными storage/edit и исчерпанной generation квотой.
`pipeline:access-runtime` при `RECOVERY_ACCESS=1` проверяет два одновременных HTTP start
при одном оставшемся результате, success всех трёх вариантов, duplicate и resume.
Запускайте эти fixtures последовательно: они временно меняют политику одного тестового
администратора и восстанавливают её в cleanup. Используйте новую колоду для каждого
editor fixture: проверка намеренно меняет сохранённое содержание.
Только изолированная fake-provider среда допустима для runtime fixture; live вызовы
приостановлены пользователем. Пяти минут на реальной модели эти проверки не доказывают.

При rollback сначала остановите workers и закройте доступ, сохраните все новые таблицы и files.
Старая версия приложения не проверяет отзыв новых сессий: её нельзя возвращать в публичный
доступ как эквивалентную по безопасности. Для восстановления используйте исправленную версию
со схемой 024. Не удаляйте usage history при отключении политики.
