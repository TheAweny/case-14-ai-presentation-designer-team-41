4. Сверить активную работу команды по связанным задачам Linear. Статус карточки не доказывает наличие кода.
5. Взять один законченный этап из раздела 19. Реализацию поручать Grok, самостоятельно читать дифф и проверять контрпримеры.
6. Не запускать сразу все направления. Максимум два крупных исполнителя и один небольшой независимый этап одновременно.
7. Обновлять журнал приёмки в конце этого документа: что действительно реализовано, проверено и осталось.

## 6. Целевая схема: смысл → возможности шаблона → размещение

Предлагаемый поток:

```text
Материалы → нормализация → профили/вычисления → факты с provenance ─┐
Цель и аудитория → уточнения → требования пользователя ──────────┤
PPTX/брендбук → профиль/индекс/TemplateCapabilities ──────────────┤
                                                              ↓
                  замороженный PreparedBuildContext
                                                              ↓
              один NarrativePlan и один SlideContent на слайд
                                                              ↓
                три детерминированных LayoutAssignment
                                                              ↓
          проверка всех вариантов → общая исправленная ревизия
                                                              ↓
                     экспорт → финальный аудит
```

Модель должна учитывать шаблон заранее, но не менять факт или аналитический тип ради
удобного слота. Данные и цель определяют, что нужно сообщить; capabilities определяют,
какими проверенными способами это можно разместить.

Если обязательный материал не помещается, возможны: другая композиция, согласованное
разделение слайда, детерминированная агрегация с provenance, ограниченное расширение макета,
либо явное сообщение о несовместимости. Нельзя молча удалить обязательные пункты или
заменить scatter на pie только потому, что в шаблоне нарисован pie.

## 7. Подготовка, контракты и provenance

Ниже проект контрактов, а не указание бездумно создать ещё один параллельный набор схем.
Сначала найти эквиваленты и согласовать с POB-148/149/150/152/153.

### PreparedBuildContext

- ID и ревизия подготовки.
- Хеши материалов, шаблона, брендбука; версии extractor/indexer.
- Явные user requirements: цель, аудитория, главная мысль, ограничения.
- Разделённые данные пользователя, принятые веб-источники, модельные гипотезы.
- Ссылки на DatasetProfile, AnalysisResult, Claim и VisualizationDecision.
- TemplateCapabilities и выбранная политика расширения.
- EffectiveModelPlan: модели ролей и происхождение выбора.
- Незакрытые вопросы и статусы полноты.

Snapshot замораживается перед сборкой. Новое уточнение создаёт новую ревизию и
инвалидирует только зависимые результаты. Сборка не подтягивает изменившийся источник посередине.

### Claim

Минимум: `claimId`, текст, тип, source reference, область действия, статус поддержки.
Для чисел: значение, единица, показатель, объект, период и преобразование.
Для производного значения: операция, входные ячейки/диапазоны, политика пропусков,
результат и версия вычислителя. Это позволяет доказать рост на 23%, даже если строка «23%»
не встречалась в исходном файле.

Различать:

- пользователь сообщил;
- точная цитата найдена;
- связь значения с конкретной ячейкой установлена;
- значение вычислено из проверенных входов;
- интерпретация модели;
- информации недостаточно/есть противоречие.

`unverified` нельзя повысить до подтверждения только потому, что другая роль той же Qwen согласилась.
Поиск числа в документе не подтверждает его объект, знак, единицу или период.

### Обязательные контрпримеры provenance

- Выручка 25%, прибыль 99% в одном абзаце: выручка 99% не подтверждена.
- Значение за 2024 и 2025: нельзя смешать число одного года с периодом другого.
- `1 025`, `1 025`, `1 025` не содержат самостоятельный показатель 25.
- `-25`, `25,7`, `25.7`, `1,25` не равны 25.
- `м`, `мм`, `м²`, `м/с`, `₽` различаются; неизвестная единица не равна отсутствующей.
- Отрицание и условие обязательны: «не выросла», «при условии пилота» нельзя потерять.
- Точная цитата с переводами строк сохраняет исходный offset и hash.
- Подготовленная моделью сводка и поисковый snippet не становятся первоисточниками.

## 8. TemplateCapabilities и компактный контекст

Текущий `GenerationProfile` уже содержит композиции, слоты, размеры, шрифты и image slots.
`CompositionNote` уже содержит kind/items/useFor/special/requiredContent и необязательные
slotSemantics/groups. Надо развить эти структуры, не создавать дублирующий каталог.

### Карточка композиции

Предлагаемые сведения для планировщика:

- стабильный patternId и назначение;
- число смысловых групп, пары heading/body;
- вместимость заголовка и каждого смыслового блока;
- допустимые visual slots с минимальным размером;
- image/QR/screenshot/logo slots с различными ролями;
- обязательный контент, которого требует макет;
- protected элементы и область допустимой вариации;
- измеренные факты отдельно от выводов индексатора;
- evidence исходного слайда/объекта для семантической пометки;
- статус usable/reference/special с объяснением.

Карточка не содержит полный XML/IR или длинный образец текста. Текст шаблона — данные,
он не получает приоритет инструкции. Не подставлять команды из образцов в system prompt.

### Отбор кандидатов

1. Детерминированно исключить несовместимые требования: нет нужного asset, данных или места.
2. Найти несколько кандидатов по смысловым группам и вместимости.
3. Передать модели краткий каталог; полный подробный layout доступен отдельным чтением.
4. После ответа проверить ID и совместимость кодом.
5. Не выбирать макет с большим числом карточек, если это заставит выдумать содержание.

Текущий notes cache в service проверяется по templateHash. В проверке подготовки проверить
также revision индексатора и хеш инструкции. Не утверждать, что текущий кеш точно неверен,
не прочитав весь путь prepare/cache invalidation.

### QR в индексе

Сейчас QR упоминается как special composition, но явной привязки URL к QR-slot нет.
Нужна типизированная способность, например asset role `qr`, а не поиск слова «QR» в имени шаблона.
Образец QR с чужим адресом не должен оставаться в экспортированной презентации.

## 9. Общий автор и три варианта: основная интеграционная работа

### Общий SlideContent

Предлагаемый объект содержит:

- `slideId`, `contentRevision`, утверждение заголовка;
- упорядоченные смысловые блоки с blockId, claimIds, обязательностью и связями heading/body;
- аналитическую визуализацию без slotId: тип, данные, единицы, source/analysis references;
- asset requests, включая QR с точным URL;
- speaker notes, которые также не могут выдумывать факты;
- missingEvidence/cannotFit как структурированные состояния.

Это внутренний смысловой результат. В нём нет координат, шрифтов и идентификаторов слотов.
Zod-схема должна быть источником правды. Генерировать её в Python только если движок
действительно будет принимать эту сущность, а не потому что все схемы надо генерировать всегда.

### Написание

Автор получает один слайд: цель, аудиторию, выбранные факты, короткую карту соседних
слайдов, ограничения кандидатов. Полный brief остаётся доступным проверяющему или
по адресному запросу, но не копируется без необходимости в каждый вызов.

Отбор фактов нельзя строить только на пересечении ключевых слов: можно потерять
отрицание или важную связь. При невозможности надёжно выделить контекст сначала
оставить больший вход, измерить его и вводить сокращение отдельной проверяемой правкой.

Числа и графики предпочтительно приходят из AnalysisResult, а не генерируются writer заново.
Один вызов автора на слайд — целевой обычный путь, а не запрет на ограниченное исправление.

### Размещение

Результат placer: patternId, связи blockId→slotId, visual placement, asset placement,
проверка геометрии и конкретный cannotFit при несовместимости.

Нужно сохранить:

- весь обязательный видимый контент;
- одинаковые данные и аналитический тип;
- порядок смысловых блоков и связь заголовок/описание;
- динамическую нумерацию отдельно от смысловых чисел;
- одинаковые speaker notes или явно определённую политику их общего исправления.

Текущая `placeSlideContent` размещает блоки по одному на слот, остальные слоты заполняет
пустой строкой и любой visual отклоняет. Её нельзя считать готовым layout solver.
Сначала добавить корректное резервирование visual slot и стратегии упаковки без потери блоков.

Пустой слот разрешается только с корректным удалением его образца/placeholder при экспорте.
Нельзя сообщить успех, оставив текст шаблона или пустую рамку с чужой подписью.

### Исправления: критически важная тонкость

Один общий writer не решает задачу, если runner затем трижды независимо перепишет текст.
Сейчас именно такие отдельные циклы critic/repair есть в `runner.ts`.

Предпочтительное решение:

1. Сформировать общую ревизию содержания.
2. Разместить её во всех трёх вариантах.
3. Собрать геометрические findings и смысловые findings с адресами blockId/claimId.
4. Для layout issue сначала сменить размещение без изменения текста.
5. Если нужен rewrite — исправить общий block, проверить сохранение обязательного смысла.
6. Создать следующую общую contentRevision и повторно разместить во всех вариантах.
7. Экспортировать только согласованный набор ревизий. Вариант не может тихо остаться на старом тексте.

Общий координатор должен исключать гонку: один вариант экспортировался, пока другой
инициировал rewrite. Нужна фаза согласования перед экспортом, а не mutable cache по ходу экспорта.

Кеш `textsBySlot` по индексу слайда не подходит: slot IDs и семантика полей различаются.
Кеш общего контента включает prepared revision и смысловой ID, не только номер слайда.
Повтор одного упавшего варианта использует сохранённый общий контент и его ревизию.

### Различимость вариантов

Варианты должны отличаться композиционно: распределением блоков, колонками, масштабом,
свободным пространством в пределах дизайн-системы. Одинаковое содержание не требует
одинакового расположения. Нельзя выдавать три копии за три варианта.

Если шаблон реально даёт только один допустимый макет, честно записать ограничение,
а не выдумывать координаты или объявлять полную различимость.

### Приёмка

- Fake provider: на N слайдов три варианта вызывают общего автора N раз на чистом проходе.
- Разные slot IDs, порядок полей, число карточек, короткие заголовки.
- Весь обязательный контент видим, не только в notes.
- Данные chart/table и contentRevision совпадают во всех вариантах после repair.
- Заголовочный макет не принимает таблицу без места.
- Отмена/ошибка одного участника не оставляет вечного ожидания общего promise.
- Повтор failed variant не переписывает историю и не создаёт новую случайную аналитику.
- Реальный export/re-import сохраняет содержание и native visuals.

## 10. Бюджет пяти минут и производительность

### Граница измерения

Фиксировать время принятия пользовательского запроса. Всё, что выполняется после него
для получения обязательных результатов, входит в elapsed: очередь, model resolution,
дочитывание материалов, повторы, аудит, экспорт и сохранение обязательных артефактов.

Подготовка может быть отдельным явным этапом до запроса генерации. Нельзя задним числом
назвать долгий шаг подготовкой и перенести timestamp старта.

В `GenerationService.start` сейчас `buildStartedAt` задаётся после чтения contentIds.
Решение: либо заранее готовый verified snapshot, либо ранний timestamp с учётом этой работы.
Один абсолютный deadline передаётся во все нижние слои; вложенный timeout не начинает новые пять минут.

### BuildBudget

Предлагаемые части одного объекта на build:

- absolute deadline и сигнал отмены;
- общий лимит transport retries;
- лимит semantic repairs и число ревизий;
- token/call accounting по ролям;
- reserve для export/render;
- причины завершения и snapshot в manifest.

AttemptBudget сейчас ограничивает повторы provider, включая несколько классов ошибок,
но service его не создаёт. Константа 110 — потолок, не доказательство SLA.
Не путать первую отправку логического вызова, retry транспорта и новый repair-вызов.
Общее ограничение должно закрывать все три уровня без двойного списания одной попытки.

Планировщик имеет catch/retry, автор имеет rewrite loop, runner — до трёх audit passes.
Их надо инвентаризировать отдельно; подключение AttemptBudget к HTTP не ограничит их автоматически.

### Предварительное распределение времени

Для первого проверяемого сценария 10–15 слайдов можно начать с инженерного бюджета:
план 15–25 секунд, общий контент 80–120, общий аудит/repair 30–45, размещение и
обязательные артефакты 60–80, резерв на очереди и сбои. Это гипотеза для настройки,
не обещание: этапы пересекаются, а суммарный deadline остаётся 300 секунд.

В документации есть historical run 281,3 секунды на GPT для 3×10 слайдов. Он не
подтверждает скорость Qwen и показывает небольшой запас до ограничения.

### Ограничения модели и запросов

- Thinking управляется проверенными capabilities и явным выбором пользователя.
- Не включать thinking автоматически «для качества» во всех ролях.
- Ограничить max output отдельно для planner/writer/reviewer/repair.
- У provider сейчас output budget растёт с номером некоторых попыток; измерить верхнюю
  границу и не позволить repair съесть весь остаток.
- Параллелизм измерить на 1/2/4 запросах; восемь параллельных запросов не гарантируют ускорение одного GPU.
- Семантическая работа и QR/вычисления/геометрия не конкурируют за model slots.
- Отдельные лимитеры image/text полезны, но общий deadline обязателен.
- Не запускать новые необязательные иллюстрации, когда они отнимают export reserve.
- При budget exhaustion возвращать точный статус частичного результата/ошибки, а не «всё готово».

### Что записывать

Wall time всего build, queue time, TTFT если доступен, input/output tokens, количество
вызовов/повторов по роли, использованная модель/ревизия, preparation hash, contentRevision,
аудит именно экспортированной версии, hashes артефактов. Не записывать ключи.

Контрпримеры: зависший fetch, игнорируемый abort, бесконечные 429, invalid JSON,
невалидный контент при валидном JSON, задержка экспорта, отмена перед повтором,
два одновременных build с независимыми бюджетами.

## 11. Выбор модели и настройки

### Фактическая текущая семантика

- `resolve(input.model)` выбирает writer по явному выбору, иначе по настройке writer.
- Planner/critic берутся из своих явно назначенных ролей.
- `resolveRole` возвращает null, если роль не назначена; service тогда использует выбранный writer.
- Rewriter работает с writer.
- Image — отдельная роль; её отсутствие допустимо.

Это не скрытый доказанный fallback bug. Реальная проблема может быть в том, что UI
показывает одну модель, а пользователь ожидает её для всех текстовых действий.

### Предлагаемое решение

Сначала сделать единый `EffectiveModelPlan` для запроса: role, modelId, connectionId,
source (`explicit-action`, `role-setting`, `writer-fallback`), thinking/effort и статус capability.
Показывать компактно по запросу/в настройках действия, сохранять в manifest.

Не менять семантику явных role overrides молча. Если нужен переключатель «эта модель для
всех текстовых шагов», сделать его явным отдельным продуктовым решением с тестами.

Основная модель по словам пользователя и конфигурации — `qwen38-27b-fp8`.
Не угадывать лицензию, точную ревизию весов, context size и vision по названию endpoint.
Использовать actual probe/данные провайдера; неизвестное хранить неизвестным.

### Тестовая матрица

- Writer выбран X, planner/critic не назначены → обе роли X.
- Writer X, planner Y назначен явно → X/Y отражаются в effective plan и manifest.
- Подключение удалено/модель отключена → понятная ошибка без скрытой замены.
- Чужое private connection не используется.
- Thinking false доходит до конкретного endpoint в поддерживаемом формате.
- Unsupported effort не выбрасывается молча.
- Text-only модель не получает изображения без подтверждённой возможности.
- Изменение URL/headers/model инвалидирует относящийся к нему capability cache.
- One-shot действие и чат одинаково трактуют model override.

Совместимость response_format/streaming уже имеет реализацию и тесты. Не переписывать
её ради новой Qwen без воспроизводимого дефекта.

## 12. Промпты и инструментарий для небольшой модели

### Принцип

Одна роль — один проверяемый результат. Уменьшать задачу, а не просто число строк промпта.
Сокращённый промпт без конкретного поведения при нехватке фактов может ухудшить результат.

| Роль                | Получает                                    | Возвращает                                            | Не делает                                      |
| ------------------- | ------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------- |
| Координатор         | краткое состояние и текущий запрос          | вопрос, план действия, вызов разрешённого инструмента | геометрию/расчёты вручную                      |
| Исследователь       | один вопрос и список разрешённых источников | короткие evidence + пробелы                           | бесконечную рекурсию агентов                   |
| Экстрактор          | порцию источника с адресами                 | факты и ссылки                                        | трактовку неподтверждённых фактов как истинных |
| Планировщик         | факты, цель, capabilities                   | один narrative plan                                   | написание трёх колод                           |
| Автор               | один слайд и релевантные факты              | общий SlideContent                                    | координаты и повторный поиск                   |
| Проверяющий         | content + относящиеся источники             | конкретные дефекты                                    | безусловное одобрение собственных догадок      |
| Редактор содержания | дефект + блок + ограничения                 | ограниченную исправленную ревизию                     | переписывание всей истории                     |
| Агент редактора     | актуальный snapshot выбранных слоёв         | typed edits                                           | произвольный JS/путь к файлу                   |

### Изменения registry

- Один язык основных инструкций; ориентир 10–15 коротких правил на роль, не самоцель.
- Удалить противоречие «заполни всё» и «не выдумывай».
- Шаблонные samples показывают форму, не являются фактами.
- Не заполнять дополнительные карточки «общеизвестной конкретикой».
- Missing evidence/cannotFit должны быть разрешёнными исходами схемы.
- Два коротких примера: нормальный ответ и нехватка доказательств/вместимости.
- Не обещать, что prompt гарантирует числа и лимиты: enforce их кодом.
- Изменение смысла → semver; manifest содержит фактическую версию и hash.

POB-160 предлагает автоматические `[МОК: …]` при пропуске вопросов. Это не было
прямым пожеланием пользователя в текущем чате. Не превращать данный пункт Linear в
молчаливое разрешение фабриковать данные. Предпочтение: явный demo mode для моков,
обычный режим — недостающие сведения/вопрос/честное отсутствие. Согласовать с командой
конфликт между «колода любой ценой» и достоверной аналитикой.

### Наборы инструментов

Не обязательно каждый ход отдавать все инструменты. Рассмотреть группы prepare,
research, build, edit с небольшим пересечением. Сначала проверить текущий gating:
часть tools уже условна по вложениям и доступности сервиса.

Нельзя выбирать toolset только по регулярному выражению сообщения так, чтобы пользователь
потерял нужную функцию. Использовать состояние продукта и явный режим; расширение
набора инструментов должно иметь безопасный путь.

Исследователь имеет максимум один уровень делегирования, call/character/time budgets,
и возвращает artifact reference + несколько цитат, а не историю поиска целиком.
Полные артефакты хранить отдельно с доступом по владельцу.

### Приёмка промптов

JSON first-pass rate, missing required facts, придуманные числа/имена, input/output tokens,
число repair, elapsed. POB-162 предлагает ≥95% валидного JSON с первого ответа на
регрессии 3 известных + 2 незнакомых шаблонов. До замера на Qwen не называть промпты
«оптимизированными под Qwen» — они лишь подготовлены к проверке.

## 13. Агент редактора: слои, актуальность и Undo

### Первый законченный этап

Чтение прикреплённых слоёв и изменение существующих объектов: текст, bbox, rotation,
ограниченный стиль. Сначала это, затем создание/удаление/перегруппировка и замена макета.

Текущие точки:

- `packages/contracts/src/chat.ts` — attachment и `slide-edit`.
- `apps/api/src/chats/chat-tools.ts` — `pointedElement`, `edit_slide`.
- `apps/web/src/lib/slide-context.ts` — перевод выделения в отправленный snapshot.
- `apps/web/src/components/assistant/slide-edit-card.tsx` — применение текста.
- `apps/web/src/components/assistant/deck-context.tsx` — bridge.
- `apps/web/src/components/editor/use-assistant-context.ts` и `editor-shell.tsx`.
- `packages/deck-ops/src/` — журнал, batch, operations.

### Snapshot

Стабильный deckId, slideId и elementId; номер слайда только для отображения.
Нужны dimensions слайда, видимые свойства выбранных элементов, locks/group membership,
и revision/hash исходных данных. Snapshot относится к моменту отправки, не к текущему
состоянию сервера.

Не ограничиваться before.text: текст может остаться прежним, а объект уже перемещён,
переформатирован или заменён. Для геометрии/стиля сравнивать затронутые свойства или
канонический hash элемента/слайда по заранее определённому контракту.

Не считать hash доказательством прав доступа. API отдельно проверяет доступ к колоде,
а snapshot не может предоставить права на чужой объект.

### Typed edit protocol

Предложение: editId, callId, target IDs, before revision/hash, список допустимых операций,
человекочитаемое описание и warnings. Никакого произвольного кода или generic JSON patch
в произвольное поле без allowlist.

Начальный allowlist:

- set-text с сохранением богатого оформления через существующий helper;
- set-box с конечными числами, положительными размерами и ограничениями холста;
- set-rotation;
- ограниченные font size/color/alignment/shape fill/stroke по типу элемента;
- replace-image только проверенным asset, отдельным этапом;
- reorder только когда проверены групповые инварианты.

Координаты и размеры в понятных единицах интерфейса tool; конверсия в EMU детерминированна.
Не заставлять Qwen одновременно держать огромные EMU и смысловые указания пользователя.

### Применение

1. Проверить target, before и locks на текущем committed draft.
2. Валидировать весь batch до первой мутации.
3. Применить одной записью журнала.
4. Запустить локальный аудит и показать конкретные изменения.
5. Undo восстанавливает весь batch; повторная доставка того же editId его не применяет заново.

Устаревшее предложение должно запросить новый snapshot. Для новых геометрических правок
не копировать кнопку старого текстового механизма «применить всё равно» без отдельного решения.
Совпадение текста после Undo не должно автоматически запускать ту же правку повторно.

Роли logo/footer/decoration и locked — разные вещи. Не запретить навсегда законную правку
логотипа, но не позволить модели обойти явную пользовательскую блокировку.
Ручное снятие блокировки остаётся пользовательским действием.

### Следующий этап: целый слайд

`docs/AGENT_SLIDE_EDITS.md` уже предлагает `revise_slide_content`, `replace_slide_layout`,
`set_slide_visual`, beforeHash и замену всего импортированного SlideIR одним commit.
Его прежняя пометка «edit_slide не меняется» относится к старому плану P2; текущий запрос
пользователя разрешает пересмотреть дизайн. Сначала обновить документ, чтобы не осталось двух противоречивых контрактов.

Замена макета требует Python compose/export/import одного слайда. SlotId нельзя считать
ElementId. Native chart/table должны вернуться нативными элементами, а не JSON в текстовом поле.
Медиа кандидата имеют устойчивые пути и права доступа, не исчезают после очистки temp.

### Контрпримеры

- Пользователь изменил текст/координаты между отправкой и ответом.
- Слайд переставлен, удалён, продублирован.
- Элемент удалён и создан другой с похожим текстом.
- Batch содержит валидную и невалидную операции: никаких частичных изменений.
- Locked элемент, член группы, невидимый или отсутствующий target.
- Отрицательный размер, NaN/infinity, размер вне холста.
- Повтор SSE, перезагрузка страницы, Undo/Redo.
- Старая сохранённая карточка без новых optional полей.
- Аудит сохранённого PPTX не объявляется аудитом несохранённого draft.

## 14. QR: от URL до сканируемого результата

### Ядро

Предлагаемое место: `packages/pipeline/src/assets/qr-code.ts`.
`qrcode` уже добавлен в manifest, но сам модуль не написан.

API по смыслу: `generateQrCode(url)` → PNG bytes, encodedUrl, sha256, width/height,
параметры кодирования. Не обращаться к модели, сети или PPTX.

- HTTP(S), разумный предел длины, запрет credentials/control characters.
- Сохранять query, hash и семантику percent encoding. Не удалять tracking/query без просьбы.
- Проверить Unicode URL и signed URL: нормализация не должна менять значение ссылки.
- Белый фон, тёмные модули, quiet zone минимум 4 модуля, фиксированные параметры.
- Не размывать, не обрезать через cover, не накладывать логотип для красоты в первом этапе.
- Минимальный физический размер зависит от числа модулей и поверхности экспорта;
  маленький слот должен дать cannotFit, а не нечитаемый код.

QR — один из случаев, когда читаемость важнее перекраски во все цвета шаблона.
Рамка и подпись могут следовать дизайн-системе; контраст/quiet zone кода обязательны.

### Происхождение и актуальность URL

URL берётся из явного запроса пользователя или проверенного результата чтения источника.
Ссылка, придуманная assistant prose, не становится разрешённым источником сама по себе.
При адресе в файле нужен reference на извлечённый материал, а не требование вручную вставить его заново.

Различать `encoded` и `reachable`. Успешное кодирование не доказывает существование сайта.
Для внешнего ресурса использовать уже существующий безопасный fetch_source в подготовке:
requested URL, final URL после redirects, fetchedAt, HTTP outcome. Учитывать, что 200
не гарантирует правильную страницу, а страница за логином может быть допустимой целью.

Не запрещать пользователю QR для собственного внутреннего ресурса только из-за того,
что сервер не может его проверить. В этом случае encode разрешён, reachability явно not-checked.
Проверки сети сохраняют SSRF-защиту; кодирование само по себе не открывает URL.

### Инструмент и редактор

Предложение: `generate_qr` в новом `apps/api/src/chats/qr-tool.ts`.
Инструмент возвращает модели компактные metadata. PNG не включается в model history.

Для UI возможен ChatPart `qr-code` с qrId, url, sha256, dimensions и bounded PNG
или защищённой ссылкой на asset. Выбрать один путь хранения и протестировать его.
Base64 в части допустим только с жёстким размером и исключением из prompt history;
для долговременного хранения предпочтителен asset ID с правами доступа.

Карточка: превью, ссылка назначения, результат проверки ресурса, скачать PNG,
вставить в текущий слайд. Вставка использует существующий MediaRegistry и журнал,
сохраняется в draft и входит в PPTX/PDF/HTML export. Просто показать картинку в чате недостаточно.

### Автоматическая генерация по шаблону

Отдельная обязательная интеграция: QR нужен не только после сборки в редакторе.
SlideContent.assetRequests содержит exact URL и QR role, LayoutAssignment привязывает
его к допустимому image/asset slot. PNG создаётся один раз и переиспользуется вариантами,
в composedSlide.images идёт fit contain. Исходный образец QR заменяется/удаляется.

Не запускать генератор иллюстраций для QR. Не использовать эвристику по названию шаблона.
Если URL отсутствует, до сборки спросить или выбрать композицию без QR при допустимости
этого решения; не оставлять QR на чужой ресурс.

### Приёмка

- Независимый decoder читает байты созданного PNG и возвращает точный URL.
- Повтор той же операции детерминирован.
- Unicode, ampersand, fragment, длинный URL, query с подписью.
- Отказ для javascript/file/data URL и credentials.
- QR повторно декодируется из рендера экспортированного PPTX/PDF.
- Вставка, reload draft, Undo и последующий export сохраняют asset.
- URL из assistant prose без источника не проходит автоматический путь provenance.

## 15. Перенос шаблона между экземплярами

### Первый этап — исходный файл

Скачать оригинальный PPTX/POTX с байтами и расширением без изменений.
Другой instance принимает его через существующий upload и строит собственный профиль.
TypeScript обслуживает поток файла, но не читает структуру PPTX.

Точки реализации:

- `apps/api/src/files/files.controller.ts`: защищённый endpoint скачивания.
- Серверный proxy в `apps/web/src/app/api/` по существующему auth pattern.
- `apps/web/src/components/templates/template-library.tsx`: пункт существующего меню.
- RU/EN тексты и download helper по принятым UI паттернам.

Доступ: свой шаблон и доступный shared; чужой private и удалённый недоступны.
Не путать право скачать доступный shared с правом менять или удалять его.
Unicode Content-Disposition, безопасный fallback filename, корректный MIME для PPTX/POTX,
понятное сообщение при отсутствии файла/ошибке.

Проверка: SHA-256 скачанного файла равен оригиналу; upload на другом экземпляре принимает
его и не зависит от прежнего ownerId/fileId. JSON-профиль не заменяет оригинал.

### Второй этап — перенос подготовленного пакета

Если требуется переносить брендбук, assets, настройки и подготовленный индекс:
версионированный bundle с manifest, original template, разрешёнными style sources,
hashes и schema version. Не включать аккаунты, ключи и внутренние абсолютные пути.

Импорт проверяет размеры, пути внутри архива, hashes и совместимость версии.
Индекс доверяется только при совпадении версии/схемы/входов; иначе переподготовка.
Этот этап не нужен, чтобы выпустить полезное скачивание оригинала.

POB-185 про пустой PPTX относится к тому же upload UI. На сервере отказ при size=0
уже есть; надо сначала воспроизвести, где UI теряет ошибку, не добавлять второй аналогичный серверный if.

## 16. Ограниченное расширение шаблона

Предлагаемая политика по умолчанию — строгое использование шаблона. Расширение является
явным пользовательским режимом/настройкой проекта, не случайным выбором модели.

Возможные уровни:

1. Использовать существующие композиции и допустимую настройку плотности.
2. Добавлять нативные графики/таблицы/QR в разрешённую content area.
3. Создавать новую композицию из типизированных примитивов и токенов дизайн-системы.

Для финала сначала уровни 1–2. Произвольная генерация дизайна, свободный canvas-код и
копирование неизвестных координат моделью в критический путь не входят.

Отступы, палитра, typography, подписи и легенды выводятся из профиля. Защищённые logo,
footer и safe areas сохраняются. Если подходящего стиля нет, fallback явно обозначен.
Аудит должен различать разрешённое расширение и нарушение шаблона.

По POB-150 эксперт допускает новый тип графика, если шаблон не подходит, но последняя
пометка карточки называет это nice-to-have. Не ставить сложный свободный layout выше
общего контента, аналитики стандартных графиков и доказанного времени.

## 17. Финальная аналитика и брендбук: стыковка с командой

### Данные

POB-148 — общие контракты, POB-149 — нормализация, POB-150 — анализ,
POB-120 — подтверждённые тезисы, POB-156 — заголовки-выводы.

Минимальный сквозной путь:

1. Extractor отдаёт таблицу с исходными ячейками, типом файла/листом/диапазоном.
2. Profiler определяет типы, пропуски, временную ось и единицы без угадывания.
3. Детерминированные операции sum/count/mean/group/filter/delta/share/histogram создают AnalysisResult.
4. Выбор визуализации ранжирует 2–3 допустимых варианта по данным и цели.
5. Заголовок формулирует вывод из AnalysisResult; число ссылается на вычисление.
6. Общий SlideContent и все три layout используют одну VisualizationDecision.
7. UI объясняет выбор графика и показывает source/provenance.

Особые случаи: zero denominator, отрицательные доли, пропуски ≠ ноль, смешанные единицы,
неоднозначные даты, дубликаты категорий, outliers, >200 строк, пустая/нетипизируемая таблица.
Не срезать большой файл первыми строками и не выдавать это за анализ всего набора.

Текущие generation contracts поддерживают только bar/column/line/pie и маленькие таблицы.
Добавление scatter/histogram/grouped/stacked/KPI требует совместного изменения contracts,
engine visuals/export, renderer/editor и тестов. Одного нового имени в enum недостаточно.

### Брендбук

POB-152/164 — extraction, POB-153 — capabilities/index, POB-125 — применение стиля.

Приоритет: явное применимое указание пользователя → применимое правило брендбука → PPTX → обозначенный fallback.
Требуются scope правила, evidence, confidence и различение измеренного/предположенного.
Не применять каждый найденный цвет как основную палитру и каждый шрифт PDF как основной.

Файл `.fig` и подключённый Figma file — разные входы. Возможности коннектора не доказывают,
что сервис умеет парсить произвольный загруженный `.fig`. Зафиксировать реально поддерживаемый путь.

Подготовить синтетические примеры style sources и dataset fixtures в репозитории, не
копируя закрытый датасет организаторов. Не обещать все форматы до их сквозной проверки.

промпты и часть инфраструктуры — Why?; аналитика/интерфейс/интеграция — TheAweny.

Каждый шаг проходит независимое ревью до следующего. Не принимать частичную интеграцию

### Волна 4. Редактор и QR

**C. Редактор.** Grok 4.7 high: chat contracts, layer tool, snapshot/bridge/journal/card.

Ошибки/статусы/терминология, export round-trip, browser scenarios, полный Qwen benchmark,

### Формат задания Grok

Каждое задание содержит:

1. Конкретное пользовательское поведение и проблему.
2. Разрешённые файлы и запрещённые общие файлы.
3. Входной/выходной контракт.
4. Инварианты и 3–5 контрпримеров.
5. Команды ограниченной проверки.
6. Требование реализовать, а не вернуть обещание.
7. Итог: changed paths, tests, known limitations, интеграционные риски.

Отчёт исполнителя — вход для ревью. Оркестратор читает изменения и выбирает собственные
проверки, которые не зеркалят реализацию. Если дефект найден, возвращает его с воспроизведением.

## 20. Проверки и критерии выпуска

### Локальные обязательные проверки

TypeScript — через Nx с актуальными project names:

```powershell
$env:NX_DAEMON='false'
yarn nx run-many '--targets=test,typecheck,lint' '--projects=contracts,pipeline,api,deck-ops,web' --outputStyle=static
yarn nx run web:e2e-chat
```

Выполнять только релевантный набор, не все проверки после каждого изменения текста.

Целевые тесты использовать с поддерживаемыми аргументами текущего Nx target.

После cross-language схем: `yarn nx run contracts:codegen`, затем проверить diff generated
files и fixture tests на обеих сторонах. Python — только uv и существующие Nx targets;
в этом checkout `engine/project.json` не найден, поэтому не выдумывать `nx engine:test`.
Найти реальную конфигурацию задач, при необходимости оформить target отдельным маленьким изменением.

### Независимая матрица

| Группа       | Минимальные сценарии                                                       |
| ------------ | -------------------------------------------------------------------------- |
| Содержание   | полный brief, без чисел, противоречивые факты, длинный обязательный пункт  |
| Шаблоны      | карточки, один body, короткий title, special asset, незнакомый шаблон      |
| Три варианта | общий content hash, разные композиции, repair во всех, retry одного        |

| UI           | ошибки видимы, keyboard, узкий экран, старые сохранённые сообщения         |

### Уровни доказательства

1. Unit: чистые функции и ошибки.
2. Integration: настоящий dispatcher/workflow/API с fake provider, не обход тестом production wiring.
3. Artifact: engine export/re-import, real render, QR decode, native chart/table.
4. Browser: действия пользователя, stale draft, Undo, скачивание.
5. Live model: нужный endpoint, first-pass JSON, факты и время всей сборки.

Успех уровня 1 не объявлять успехом уровней 3–5. Наличие теста не означает, что сценарий был запущен.

### Статус результата

Разделить техническую готовность артефакта и качество: complete/requires-review/failed,
с точной причиной и revision. Отсутствие аудита — unknown, не ноль ошибок.
Карточка результата перечисляет реально готовые варианты. Таймер заканчивается только
по установленной границе обязательных артефактов.
