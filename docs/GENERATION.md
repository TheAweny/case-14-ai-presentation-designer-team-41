# Реальная генерация презентации

Рабочий путь в `main` на 29 сентября 2026: один бриф раскладывается **тремя вариантами**
(`dense`, `balanced`, `airy`) параллельными прогонами с общим планом, аудитом, PPTX/PDF/PNG и
персистентным API. Это подтверждение транспорта, экспорта и времени, а не финальной ML-оценки
качества на любом неизвестном шаблоне или production SLA.

## Запуск

Нужны Node 22.13+, Yarn, Python 3.12/uv, LibreOffice (`soffice`), Poppler (`pdftoppm`)
и fontconfig (`fc-match`). Шрифты выбранного шаблона нужны, чтобы превью совпало с
файлом; без них колода всё равно собирается. Dockerfile движка устанавливает
инструменты и Play с SIL OFL. На macOS шрифты из `infra/fonts/Play` нужно установить в
`~/Library/Fonts`; движок создаёт отдельный fontconfig для headless LibreOffice.

В игнорируемом `.env` задаются `MODEL_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` из `.env.example`.
Не сохранять ключи в исходниках, run manifests, документации и shell history.

```bash
yarn install --immutable
uv sync
yarn nx run-many -t build -p pipeline,engine-client
uv run uvicorn engine.api:app --host 127.0.0.1 --port 8000
# В другом терминале:
node --env-file=.env --import tsx scripts/generate-presentation.mts \
  /absolute/path/template.pptx /absolute/path/brief.md 10
```

CLI сначала подготавливает профиль, затем запускает измеряемую генерацию. Результат —
`runs/<uuid>/deck.pptx`, `previews/deck.pdf`, PNG всех слайдов, `plan.json`, `deck.json`,
`audit.json`, `images.json`, `events.jsonl`, `manifest.json`. При отказе записывается
`failure.json`; незавершённая работа не объявляется готовой.

API и CLI можно гонять и по конфигу прогона (`configs/run.example.yaml`): `lct generate
<config.yaml>` строит план один раз, раскладывает его перечисленными в конфиге вариантами
(от 1 до 3), прогоняет детерминированный и контекстный аудит и пишет в `runs/<run-id>/`
план, слайды, аудит и `manifest.json` каждого варианта.

## Почему используется исходный шаблон

Docker-движок содержит оригинальные Play и Inter (включая Inter SemiBold). Для других
гарнитур задайте `TEMPLATE_FONTS_DIR` в `.env`: каталог монтируется только для чтения,
а стартовый скрипт обновляет fontconfig до запуска HTTP-сервера. По умолчанию это
игнорируемый `data/fonts`. На текущем macOS-хосте четыре начертания Arial скопированы
из системного каталога в `data/fonts`; они исключены из Git и Docker build context.
Прямой mount `/System` запрещён настройками Docker Desktop. После изменения каталога:
`docker compose up -d --force-recreate engine`. Если исходной гарнитуры нет, сборка
продолжается: в `.pptx` остаётся её имя, превью LibreOffice рисует заменой, а ответ
движка (`missingFonts` и `warnings`) и ход прогона сообщают об этом. Подробнее —
`infra/fonts/README.md`.

Временный каталог рендера создаётся внутри каталога результата. Поэтому публикация
PDF/PNG через атомарный rename не пересекает файловые системы контейнера и bind mount
`runs/` (раньше этот случай приводил к `EXDEV: Invalid cross-device link`).
Проверка 2026-09-27 через Docker API: Shablon_PROD, 10 слайдов — 16.150 с; VK Education,
10 слайдов — 12.203 с до состояния done и готовых артефактов. Скачивание PPTX/PDF,
контрольные суммы и persisted listing проверены. Это техническая проверка, не ML-оценка
качества; во втором прогоне сохранено замечание критика к пустому полю на слайде 7.

Python извлекает композиции реальных слайдов и наследование placeholder → layout → master.
В профиль попадают шрифты, кегли, границы, внутренние поля, межстрочные интервалы и ёмкость.
Экспорт клонирует выбранные моделью слайды внутри исходного PPTX и заменяет нативный текст,
не пересобирая брендинг по приблизительной палитре. Сохраняются фон, тема, мастер-макеты,
расположение, интервалы и существующий декор. В TypeScript нет разбора или изменения PPTX.

Профиль не даёт модели произвольных координат: модель выбирает подходящие исходные композиции,
их порядок и содержание. Это минимальный безопасный путь к первому template-faithful результату.
Свободная перестройка всех объектов и создание новых native charts/tables вне композиций
в этот режим не входят.

## Mastra и обращения к модели

- **Подготовка (вне тайминга).** Для каждого шаблона один раз читается generation profile,
  агент `template-indexer` описывает композиции (для чего каждая, сколько элементов, какие
  страницы — reference), а библиотека получает PNG всех слайдов шаблона. Индекс кешируется в
  Postgres вместе с профилем и пересобирается, если изменился хеш шаблона или версия промпта.
  Отказ индексатора не блокирует колоду: планировщик просто работает без заметок.
- **Один planner на бриф.** `deck-planner` строит план один раз: о чём каждый слайд, какая
  композиция, какой картинки он просит. Один и тот же план (`SharedPlan`) и одни и те же
  иллюстрации (`SharedIllustrations`) используются всеми тремя вариантами.
- **Три варианта параллельно.** Каждый вариант — отдельный прогон (`generatePresentation`) со
  своим writer'ом: один и тот же план раскладывается под плотность варианта. `dense` — самые
  заполненные макеты, `balanced` — средние, `airy` — просторные; писатель получает поправку и
  перепланирует, если один макет занял больше трети колоды. `foreach` запускает writer по
  слайдам с concurrency 3.
- **JSON автора** содержит объект `textsBySlot` с обязательными ключами всех полей;
  это исключает повторные/пропущенные ID из свободного массива bindings.
- **Переполнение** передаётся slot-rewriter: он предлагает три законченные формулировки.
  Код выбирает помещающийся вариант, но не обрезает слова и не уменьшает шрифт. Отдельный
  агент `copy-fitter` укорачивает заголовки и буллеты, которые не влезли, до заданной длины,
  сохраняя факты и цифры.
- Движок проверяет длину текста по метрикам шрифта и доступным строкам, включая соседний
  текстовый блок. Проверка повторяется перед экспортом.
- Контекстный critic той же модели предлагает правки; до двух раундов repair проходят через
  отдельный Mastra workflow. Остаточные смысловые замечания сохраняются как предупреждения
  `content-review-required`, не скрываются и не приравниваются к успешной ML-оценке.
- Детерминированное переполнение блокирует экспорт. Отсутствующий выбранный шрифт также
  блокирует faithful render вместо молчаливой замены гарнитуры.
- Лимитер провайдера допускает `MODEL_MAX_CONCURRENCY` (по умолчанию 8) HTTP-запросов на
  процесс, совместно для всех прогонов и чата, и адаптивно сокращает их после 429; несколько
  процессов требуют внешнего согласования квоты команды 10. Deadline каждого прогона —
  290 секунд, на экспорт, аудит и рендер после ожидания картинок резервируется минута.
- Текстовые роли используют Qwen3-30B-A3B-Instruct-2507 (30.5B, потолок кейса — 35B), зрение —
  Qwen3-VL-8B-Instruct. Thinking отключён; схемы проверяются провайдером и Zod. До трёх попыток
  при 429/502/503 или усечённом JSON. Параметры ролей читаются из `registry/agents/*/agent.yaml`.

Архитектурные точки расширения: `TextProvider` для endpoint, registry для инструкций,
`GenerationProfile` для новых свойств шаблона, `ImageProvider` для генератора изображений.

## Иллюстрации

Слот картинки (`imageSlots` композиции) находит парсер движка: picture-плейсхолдер или большая
пустая залитая карточка, на которой ничего не нарисовано (`placeholder` и `panel`). Рамки меньше
8% площади слайда (портреты, иконки, QR) слотами не считаются. Фото и фирменный арт шаблона —
его дизайн, их не заменяем.

1. Планировщик получает `imagesAvailable` и число `imageSlots` у каждой композиции. Без модели
   изображений композиции со слотами ему не предлагаются, пока без них хватает макетов.
2. Сразу после плана (`onPlan`) начинается рисование, параллельно с написанием текста. Агент
   `illustrator` (текстовая модель) пишет промпт по `imageQuery`, утверждению слайда, аудитории и
   стилю шаблона: палитра `designSystem.palette`, тёмный или светлый фон, форма рамки. Текст,
   логотипы, водяные знаки, QR и узнаваемые лица запрещены в промпте.
3. `SharedIllustrations` рисует слот слайда один раз на бриф: три варианта с одной формой рамки
   получают одну картинку. Размер — ближайший к боксу из 1024x1024, 1536x1024, 1024x1536.
4. Перед экспортом прогон ждёт картинки, пока от бюджета 290 с не останется минута на экспорт.
   Не успевшая или не нарисованная картинка оставляет слот пустым.
5. Движок вставляет картинку нативно (`add_picture`) в бокс и геометрию слота: `cover` обрезает
   по боксу без искажения пропорций, `contain` вписывает целиком. Слот без картинки экспорт
   удаляет, так что белых прямоугольников и пустых рамок не остаётся. Проверка аудита
   `empty-image-slot` ловит рамку, оставшуюся без картинки.

`images.json` каждого варианта хранит слот, запрос, промпт, seed, размер, модель и статус
(`generated`, `failed`, `timed-out`). Картинку, которую сервер не отдал, ничем не подменяем.
Манифест пишет агента `illustrator`, модель изображений и время этапа `illustrating`.

Модель изображений берётся из роли «Иллюстратор» в настройках, иначе из `IMAGE_BASE_URL` вместе с
`IMAGE_MODEL`. `IMAGE_PROVIDER=fake` рисует однотонные картинки без сети: так проходят тесты и
офлайн-демо. Проверка 2026-09-29, шаблон ЦУ, `IMAGE_PROVIDER=fake`: три варианта за 90 с, этап
иллюстраций 20–45 с, картинки в слотах обложки, фото-слайдов и рамки устройства.

## API и сохранение

Все маршруты API с примерами запросов и ответов описаны в Swagger: `/api/docs` (страница в теме
интерфейса, открыта без входа) и `/api/docs-json` (OpenAPI 3.0). Схемы тел и ответов строятся из
тех же Zod-контрактов `packages/contracts`, что проверяют данные в коде, поэтому описание не
расходится с API. Маршруты, которые браузер через `/api/backend` не видит, помечены «только для
сервера веба».

При загрузке весь PPTX разбирается в профиль, но для обложки LibreOffice экспортирует
только первую страницу, а Poppler растеризует только её. Оба процесса делят бюджет
20 секунд, меньший стандартного HTTP-таймаута движка (30 секунд). Если превью не удалось,
возвращается профиль с `previewDataUrl: null`; экспорт готовой колоды по-прежнему рендерит
все слайды. Ошибки движка при загрузке получают понятные статусы 422/503/504,
а интерфейс показывает сообщение API. Это не гарантирует загрузку произвольно большого
файла за 30 секунд: сам парсинг и передача данных тоже занимают время.

Регрессионная проверка 2026-09-27: внешний шаблон ЦУ, 166 слайдов, 49 208 895 байт.
До исправления Docker API возвращал 500 через 30.444 секунды; после — 202 за 10.289
секунды с валидным профилем всех 166 слайдов и PNG обложки. Профиль и превью подтверждены
через сохранённый список шаблонов. Это измерение загрузки, не генерации новой колоды.

1. `POST /files/template` с multipart `file`: сохранение и исходный разбор.
2. `POST /generation/prepare` с `{templateId}`: generation profile в Postgres, индекс композиций
   и отрисовка слайдов шаблона для библиотеки. `GET /generation/prepare/:templateId` показывает
   ход подготовки.
3. `POST /generation` с `{templateId, brief, slideCount?, outline?, contentIds?, projectId?, seed?, model?}`:
   сервис запускает **три прогона сразу** (`dense`, `balanced`, `airy`) с общим планом;
   `model` — `{connectionId, modelId}` из настроек моделей, без него — модель роли writer или
   подключение из `.env`. Каждый вариант — отдельный `run-*` с событиями и артефактами,
   библиотека показывает один build.
4. `GET /runs/:id` и `GET /runs/:id/events?after=N`: сохранённое состояние/прогресс.
5. `GET /generation/:id/deck` — колода для редактора: слайды, прочитанные движком из готового
   `.pptx`, с картинками из `media/`; `GET /generation/:id/previews` — PNG слайдов;
   `GET /generation/:id/artifacts/deck.pptx | deck.pdf | slides.zip | manifest.json | slide-N.png`.
6. `POST /generation/:id/export` — экспорт отредактированной колоды: нативные PPTX и PDF, а для
   PNG и HTML — отрендеренные превью; `GET /generation/:id/exports/:exportId/:name` отдаёт файл.
7. `PATCH /generation/:id` (название, проект) и `DELETE /generation/:id` (весь build).
8. `GET /generation` — завершённые колоды после повторного открытия, по одной на build.

Все маршруты, кроме `GET /health`, требуют заголовок `x-lct-service-token` со значением
`API_SERVICE_TOKEN`: API отвечает только веб-серверу. Браузер ходит через `/api/backend/...`
веб-сервера, который проверяет сессию и добавляет токен. Колоды и шаблоны принадлежат
аккаунту, загрузившему их: чужой объект отвечается как отсутствующий.

Повторяемый live smoke для уже загруженного шаблона:

```bash
API_URL=http://localhost:3001 API_SERVICE_TOKEN=... node --import tsx scripts/smoke-generation-api.mts \
  TEMPLATE_UUID /absolute/path/brief.md 10
```

Smoke проверяет state `done`, число слайдов, скачивание обоих файлов, совпадение SHA-256 с
manifest и наличие колоды в persisted listing. Ключ нужен только API, не браузеру.

## Проверки и ограничения

Offline tests не обращаются к Yandex. Проверяются ограниченная параллельность, JSON, отмена,
лимитер, repair/failure, публикация артефактов, наследование шрифта, геометрия, переполнение,
соседние блоки и missing-font gate. Проверки проекта: Nx tests/typecheck/lint/build,
pytest, Ruff, Pyright, import-linter, воспроизводимость codegen.

Ограничения текущего режима:

- три варианта запускаются всегда (конкурсный gate); CLI-конфиг позволяет запросить 1–3;
- вход для генерации — brief и txt/md/csv/tsv, не полноценный PDF/DOCX/XLSX content adapter;
- charts/tables рисуются нативными объектами внутри выбранных композиций; ряд
  reference/неизменяемых растровых страниц planner не предлагает;
- если шрифта шаблона нет на сервере, `.pptx` сохраняет его имя, а превью рисуется заменой и помечается предупреждением; установка шрифта внутрь файла не реализована;
- контекстный аудит — предварительная помощь, окончательное качество оценивает ML-команда;
- редактор открывает готовую колоду и экспортирует правки в PPTX/PDF/PNG/HTML, но импорт
  произвольного пользовательского PPTX в редактор и полный round-trip всех свойств
  (объединение ячеек, коннекторы, сложные эффекты) не реализованы;
- PDF и PPTX экспортируются движком; PNG — архивом превью, HTML — страницей, собранной на
  клиенте из PNG-превью; hosted `latest` не гарантирует воспроизводимость весов или побитовую
  повторяемость;
- прерывание HTTP к движку не гарантирует немедленную остановку уже начатого LibreOffice;
