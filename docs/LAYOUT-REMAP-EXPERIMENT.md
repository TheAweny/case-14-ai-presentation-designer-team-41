# Сравнение выбора макетов с сохранением структуры

Эксперимент не добавляет общего автора текста. План по-прежнему строится один раз,
а писатели получают композицию своего варианта. Поведение API по умолчанию не меняется.

## Два режима

- `density` — прежний алгоритм и режим по умолчанию: при отсутствии подходящего макета
  с тем же числом содержательных блоков допускается разница в один блок.
- `preserve-block-count` — необязательный режим: замена только на макет с тем же числом
  блоков. Если такого кандидата нет, сохраняется исходная композиция. Ограничения на
  обложки, специальные макеты, внешние ресурсы и вместимость остаются прежними.

Число блоков — число слотов `writerSlots` без роли `title`. Нумерация и даты уже исключены
из `writerSlots`; зеркальные копии не входят в записываемые слоты. Это приближение структуры:
несколько полей могут принадлежать одной карточке. Одинаковое число полей само по себе не
гарантирует одинаковую семантику.

Программный запуск генерации принимает `layoutRemapPolicy` в `GenerateOptions`.
Отсутствие значения и `density` ведут себя одинаково. Выбранный режим записывается в
manifest как ревизия конфигурации `layout-remap-policy` версии `1.0.0`; в хеш попадает
имя режима. Переключателя режима в пользовательском интерфейсе нет.

## Воспроизводимое структурное сравнение

Команда ждёт `CompositionPlan`, а не `plan.json` из каталога варианта. Runner пишет в
`plan.json` массив уже написанных слайдов: у элемента есть `index`, `title`, `slide`
с текстами слотов и `imageQuery`. Этот файл схема сравнения не принимает.

`CompositionPlan` содержит `audience`, `goal`, `title` и `slides`. У слайда есть
`patternId`, `purpose`, `imageQuery` и `sourceEvidence`, но нет готового текста слотов.
API сохраняет общий план отдельно, в `runs/<run-id>/composition-plan.json`
(`apps/api/src/generation/generation.service.ts`, запись общего плана). CLI генерации
пишет тот же объект в `composition-plan.json` каталога запуска. Идентификатор вида
`source-slide-N` не доказывает, что план и профиль относятся к одному шаблону.

Синтетический пример уже лежит в игнорируемом каталоге и подходит как вход:

```powershell
yarn nx run pipeline:compare-layout-remap -- --plan runs/remap-experiment/synthetic-plan.json --profile runs/remap-experiment/synthetic-profile.json --index runs/remap-experiment/synthetic-index.json --images-available false --output runs/remap-experiment/cli-comparison.json
```

Профиль — `GenerationProfile`, индекс — необязательный `StoredTemplateIndex`. Это
подготовленные JSON, не файлы PPTX. Команда не обращается к модели и движку. Обе политики
получают один план и тот же отбор композиций, что основной пайплайн. Отчёт содержит
выбранные макеты, изменения числа блоков и ёмкости, разнообразие макетов и условия
сравнения. В отчёте явно сказано, что сравнение структурное и не оценивает качество
колоды или время сборки.

Входы валидируются схемами. Несовпадающий хеш индекса, неизвестные или повторяющиеся
идентификаторы макетов и план, использующий исключённые текущим каталогом композиции,
останавливают сравнение. Происхождение сохранённого плана нужно проверять по manifest.
Профиль и индекс должны соответствовать условиям генерации, включая доступность
иллюстраций.

## Результат текущего локального этапа

Проверен специально составленный пример с 12 слайдами:
`runs/remap-experiment/synthetic-plan.json`, `synthetic-profile.json` и
`synthetic-index.json`. Повторный запуск команды выше 2026-10-18 записал
`runs/remap-experiment/cli-comparison.json` и совпал с ранее сохранённым
`synthetic-result.json`.

У `dense` режим `density` меняет число блоков на 11 слайдах и выбирает 3 разных макета.
`preserve-block-count` меняет число блоков на 0 слайдах и оставляет 2 макета. У balanced
и airy в этом примере изменений нет: balanced сохраняет план, а для airy подходящей
замены с допустимой ёмкостью не нашлось. Пример показывает компромисс алгоритма, а не
частоту проблемы на реальных презентациях и не качество текста.

Для сохранённой реальной колоды из 12 слайдов заново извлечён профиль исходного шаблона
из 137 композиций (`runs/remap-experiment/profile.json`). Совпадение шаблона проверено
по хешу. Старый план содержит композицию, которую текущий каталог исключает; инструмент
отклоняет такой вход. План не подменялся вручную, результат не учитывается как успешное
сравнение качества.

Данные и отчёты находятся в игнорируемом `runs/remap-experiment/`. Синтетические JSON
этого каталога в Git не входят. Воспроизведение структурного сравнения остаётся в тестах
`remap-evaluation.spec.ts` и `remap-cli.spec.ts`, которые входят в отдельный stacked PR
поверх `theaweny/template-aware-agents`.

## Что нужно измерить до смены режима по умолчанию

На одинаковых материалах и незнакомых шаблонах сравнить оба режима с одной моделью,
параметрами и доступностью изображений. Сначала использовать один сохранённый совместимый
`composition-plan.json` для изоляции выбора макетов, затем проверить полные сборки.
Чередовать порядок режимов.

Измерять время от запроса до готовности всех трёх вариантов, токены, повторные запросы,
ремонты текста, экспорты и пропуски аудита. Отдельно оценивать сохранение чисел, единиц,
условий и отрицаний, читаемость, связность и различимость вариантов. Сохранение числа
полей и успешный экспорт не являются оценкой качества текста.

`density` остаётся режимом по умолчанию. `preserve-block-count` не становится основным
до сравнения реальных результатов. Ускорение и выполнение пятиминутного ограничения на
целевой Qwen этим структурным этапом не подтверждены.

## Что этот этап не делает

Общий автор содержимого для трёх вариантов не реализуется и не является следующим
автоматическим шагом. После консультации с Astra его отложили до измерений: сначала
нужно понять, как смена макетов меняет структуру и стоимость сборки. В этом эксперименте
общий автор, QR-инструмент и адресное редактирование слоёв не добавлялись. Экспорт
исходного PPTX/POTX уже принят первым этапом в `c80ceef`; новый bundle экспорта этим
этапом не делается.
