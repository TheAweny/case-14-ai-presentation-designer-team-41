## 1. Обзор и запуск

[↑ к оглавлению](#оглавление)

Целевой сервис собирает презентацию в стиле произвольного загруженного шаблона: разбирает чужой
`.pptx` как набор правил (дизайн-система, макеты, визуальные паттерны), принимает контент из
`.pptx`, `.pdf` или `.html`, строит по нему колоду на 10–15 слайдов, проверяет её аудитом и
экспортирует в `.pptx`, `.html` и `.pdf`.

Решение открытое и **не затачивается под конкретные шаблоны**: всё, что зависит от шаблона,
берётся из профиля шаблона, полученного при разборе файла. Описание кейса — в
[docs/CASE.md](docs/CASE.md).

### 1.1. Статус соответствия

Требования и доказательства их выполнения перечислены в
[docs/COMPLIANCE.md](#6-соответствие-требованиям). В `main` работает реальная генерация тремя
вариантами: Mastra → Qwen/Yandex → исходные композиции шаблона → PPTX/PDF/PNG, с общим
планом, индексом шаблона, иллюстрациями, fit-check/repair, детерминированным и контекстным
аудитом и сохранением прогресса. Три варианта на шаблонах организаторов собирались за
23–35 секунд (`docs/EVIDENCE.md`); это технические замеры, не SLA и не holdout.
Инструкция, evidence и ограничения — в [docs/GENERATION.md](#3-генерация-презентации).

### 1.2. Как это устроено

Граница между языками проходит по признаку «есть ли здесь модель»:

- **TypeScript** — продукт и оркестрация: Next.js (интерфейс), NestJS (API), Mastra (агенты и
  workflow). Все обращения к моделям происходят только здесь, как и контекстные проверки аудита.
- **Python** — детерминированный движок документов: разбор `.pptx`, вёрстка, графики и таблицы,
  экспорт, рендер в PNG, детерминированные проверки аудита. Вызовов модели в движке нет.

Подробнее — в [docs/ARCHITECTURE.md](#2-архитектура).

### 1.3. Требования к окружению

| Что    | Версия                                                       |
| ------ | ------------------------------------------------------------ |
| Node   | 22.13+ (`.nvmrc`)                                            |
| Yarn   | 4.x через Corepack, **только yarn**                          |
| Python | 3.12 (`.python-version`)                                     |
| uv     | 0.12+, **только uv**                                         |
| Docker | для запуска всей связки, включая LibreOffice в образе движка |

### 1.4. Установка одной командой

```bash
curl -fsSL <raw-url>/install.sh | bash     # или ./install.sh из клона репозитория
```

Установщик проверит git, Node.js 22 и Docker, склонирует репозиторий в `~/lct26` (или
возьмёт тот, из которого запущен), соберёт CLI, положит команду `lct` в `~/.local/bin` и
запустит мастер `lct onboard`:

1. как запускать: Docker Compose или локально для разработки;
2. откуда брать модель: Yandex AI Studio (ключ и ID каталога), любой OpenAI-совместимый API
   или офлайн на записанных ответах; соединение сразу проверяется;
3. администратор интерфейса: почта, имя, пароль; ключ подписи сессий создаётся сам;
4. проверка портов, запись `.env` (доступен только владельцу), сборка, запуск и ожидание
   `/health`.

Без вопросов, например в CI:

```bash
./install.sh --yes --provider ai-studio --api-key KEY --folder-id b1g... \
  --admin-email you@example.com --admin-password '...'
```

После установки:

| Команда                       | Что делает                                                 |
| ----------------------------- | ---------------------------------------------------------- |
| `lct start`, `stop`, `status` | сервис в Docker Compose                                    |
| `lct logs [сервис]`           | логи                                                       |
| `lct user admin [почта]`      | администратор установки; остальных он заводит в интерфейсе |
| `lct doctor`                  | проверка окружения, модели, аккаунтов и сервиса            |
| `lct generate <config.yaml>`  | генерация колод по конфигу прогона                         |

#### Модель

Модели перечислены в `configs/models.yaml` (подробности в [docs/MODELS.md](#4-модели)).
Сервис говорит с любым рантаймом с OpenAI chat API: свой vLLM или llama.cpp либо внешний
провайдер моделей с открытыми весами. В `.env` задаются `LLM_BASE_URL`, `VLM_BASE_URL`,
`MODEL_API_KEY` и, если провайдер называет модели по-своему, `LLM_MODEL` и `VLM_MODEL`.
`MODEL_PROVIDER=fake` отвечает записанными ответами из `registry/recordings/` без сети и GPU,
`MODEL_PROVIDER=record` записывает ответы настоящей модели.

### 1.5. Установка вручную

```bash
corepack enable
yarn install
uv sync
```

### 1.6. Локальный запуск

```bash
cp .env.example .env
docker compose up -d postgres
set -a && source .env && set +a
yarn nx run api:serve     # NestJS на http://localhost:3001
yarn nx run web:serve     # Next.js на http://localhost:3000
uv run uvicorn engine.api:app --reload --port 8000   # движок
```

API и CLI используют PostgreSQL из `DATABASE_URL`. Compose публикует локальную БД на порту
`5433`, чтобы не конфликтовать с часто установленным системным PostgreSQL на `5432`.

### 1.7. Запуск в Docker

```bash
cp .env.example .env
docker compose up --build
```

Поднимаются четыре контейнера: `web`, `api`, `engine` и `postgres`. Движок наружу не публикуется
и доступен только для API. PostgreSQL хранит состояния прогонов и метаданные артефактов в
именованном volume; PPTX, превью и входные файлы остаются в `runs/`.

### 1.8. Запуск по конфигу

```bash
yarn nx run cli:build
node apps/cli/dist/main.js generate configs/run.example.yaml
```

Конфиг прогона описывает шаблон, контент, число слайдов, варианты вёрстки, профиль аудита,
модели, seed и цель колоды. Команда строит план, раскладывает его тремя вариантами, проводит
детерминированный и контекстный аудит, выгружает `.pptx` и `.pdf` и пишет в
`runs/<run-id>/` всё, что нужно для воспроизведения: план, слайды и аудит каждого варианта и
`manifest.json` с хешами файлов, временем по стадиям и ревизиями агентов, промптов, моделей,
шаблона и конфигов. Движок должен быть запущен (`ENGINE_URL`, по умолчанию
`http://localhost:8000`), модель задаётся как в разделе «Модель».

### 1.9. Проверки

```bash
yarn lint && yarn typecheck && yarn test && yarn build   # TypeScript
yarn lint:py && yarn typecheck:py && yarn test:py        # Python
yarn boundaries:py                                       # границы слоёв движка
yarn codegen                                             # Zod -> JSON Schema -> Pydantic
yarn licenses                                            # политика лицензий зависимостей
yarn docs:audit                                          # пересборка docs/AUDIT.md
```

### 1.10. Ограничения

- Анализ входных данных и пользовательского шаблона выполняется на отдельном подготовительном
  этапе. После отправки пользователем запроса все три варианта колоды с обязательными
  артефактами должны быть готовы не более чем за 5 минут. План строится один раз и
  переиспользуется вариантами, а обращения к моделям по слайдам идут параллельно.
- Колода — 10–15 слайдов; одобренный план (чат, режим «План») допускает 10–60.
- API всегда собирает три различимых варианта (`dense`, `balanced`, `airy`) — это конкурсный
  gate. CLI-конфиг (`configs/run.example.yaml`) позволяет запросить от 1 до 3 в `layoutVariants`.
- Входные PDF/HTML проходят отдельные content adapters и нормализацию в `ContentPack`; PPTX
  остаётся форматом шаблона и также может быть источником контента.
- Промпты и конфиги агентов лежат отдельными файлами в `registry/agents/`, в коде их нет.
- Датасет организаторов, содержимое `runs/` и `.env` в репозиторий не попадают.
- Шрифты пользовательского шаблона берутся из самого файла во время работы; в образы кладём
  только свободные шрифты.

## 2. Архитектура

[↑ к оглавлению](#оглавление)

Документ описывает пайплайн и границы слоёв. Разделы, помеченные «дополняется по мере
реализации», сейчас фиксируют контракт, а не готовый код.

### 2.1. Пайплайн

```
шаблон .pptx ──► [1] парсинг ──► профиль шаблона ─┐
                                                  ├─► [3] вёрстка ──► IR слайдов ──► [4] аудит ──► [5] экспорт
контент-пак ───► [2] план колоды ─────────────────┘                        ▲
                                                                           └── правки от агента
```

1. **Парсинг шаблона** (Python, `engine.parser`). Загруженный `.pptx` разбирается как набор
   правил: палитра, шкала кеглей, сетка, мастер-макеты, повторяющиеся паттерны фигур. Результат —
   профиль шаблона. Минимальный vertical slice уже извлекает размер слайда, видимые solid-цвета и
   типографику из реального файла, не ветвясь по его имени.
2. **План колоды** (TypeScript, `@lct/pipeline`). Агент строит план: о чём каждый слайд, какой у
   него тип, какие данные он показывает. План строится **один раз** и переиспользуется всеми
   вариантами вёрстки — это ключевая оптимизация под общий бюджет в 5 минут для всех трёх
   вариантов после отправки пользователем запроса на генерацию.
3. **Вёрстка** (Python, `engine.layout` и `engine.visuals`). Детерминированная: план плюс профиль
   дают IR слайдов. Если текст не влезает, слой возвращает сигнал о переполнении и не трогает
   текст сам; переписывание делает агент на стороне TypeScript. Графики, таблицы и схемы
   собираются нативными фигурами, а не картинками.
4. **Аудит**. Детерминированные проверки над SlideIR (`@lct/slide-audit`) измеряют геометрию,
   контраст, шрифты, остатки заглушек; редактор запускает их после каждой правки, пайплайн — после
   вёрстки. Проверки, которым нужен сам `.pptx` или его рендер, — в `engine.checks`. Контекстные
   проверки (`@lct/pipeline`) читают смысл:
   отвечает ли заголовок содержанию, подтверждён ли тезис контент-паком. Пользователь видит
   findings и выбирает, какие правки применить.
5. **Экспорт и рендер** (Python, `engine.export` и `engine.render`). `.pptx` собирается поверх
   исходного шаблона, из него же получается `.pdf`, а рендер в PNG питает превью, визуальные
   проверки и экспорт `.png`/`.html` (HTML — страница со слайдами, собранная из этих превью на
   стороне TypeScript), поэтому пользователь экспортирует ровно то, что видел.

#### Минимальный editable vertical slice

`POST /v1/editable-decks` в `engine.api` принимает локальный путь к template, путь результата и
fixture-контент с title/body для 1–15 слайдов. API соединяет независимые слои: parser строит
`DesignSystem` с доказательствами, layout создаёт text-элементы `SlideIR`, а export открывает template и записывает
PPTX с нативными PowerPoint text boxes. Внутри endpoint нет модели и нет условий по имени или
стилю конкретного template. Контракт запроса/ответа — Zod-схемы `EditableDeckRequest` и
`EditableDeckResponse`, из которых генерируются Pydantic-модели. Smoke-тест повторно открывает
выход через `python-pptx` и конвертирует его headless LibreOffice.

### 2.2. Три варианта вёрстки

План колоды пишется один раз, а три варианта раскладываются на одном и том же профиле шаблона.
**Ось различий — плотность.** Мы выбрали её, потому что это единственная ось, которую каждый
шаблон задаёт сам: у любого файла есть макеты разной заполненности и шкала кеглей. Порядок
слайдов и формулировки у всех трёх вариантов одинаковые, поэтому варианты сравнивают вёрстку,
а не содержание, и ни один не может потерять или добавить факт.

| Вариант    | Макеты шаблона       | Кегль текста                                | Внутри слота                                         |
| ---------- | -------------------- | ------------------------------------------- | ---------------------------------------------------- |
| `dense`    | самые заполненные    | наименьшая ступень body/bullet              | длинный список делится на две колонки гаттером сетки |
| `balanced` | средние по плотности | ступень body                                | как задумано макетом                                 |
| `airy`     | самые просторные     | крупнейшая ступень, в которую текст влезает | короткий текст центрируется по вертикали             |

Три варианта производятся двумя путями:

- **Основной путь генерации** (`packages/pipeline`): API запускает три прогона
  `generatePresentation` параллельно (`dense`, `balanced`, `airy`), каждый со своим
  писателем, но с общим планом `SharedPlan` и общими иллюстрациями `SharedIllustrations`.
  Модель выбирает композиции, но не генерирует координаты; `dense` получает поправку и
  перепланирует, если один макет занял больше трети колоды.
- **Детерминированный слой движка** (`engine.layout.build_slide_ir`, `POST /v1/layouts`):
  тот же план раскладывается без модели тремя способами (в тестах и eval).

Правила, которые держат варианты честными:

- паттерн выбирается, только если в нём есть место для всего, что несёт слайд: заголовка,
  подзаголовка, текста; макеты с пустым слотом картинки или графика уступают остальным;
- если в шаблоне есть хотя бы два подходящих макета, варианты получают разные; если один —
  различаются кеглем и раскладкой внутри него;
- размеры берутся только из шкалы шаблона, колонки — из гаттера его сетки, поэтому все три
  варианта одинаково проходят проверки шаблона в аудите;
- вёрстка измеряет текст так же, как аудит, и если она сочла текст влезающим, аудит не найдёт
  там переполнения; то, что не влезает, возвращается сигналом `overflow` для агента.

Тесты `engine/tests/test_layout_variants.py` проверяют, что отпечатки трёх вариантов попарно
различаются, а тексты совпадают до слова.

### 2.3. Почему граница между Python и TypeScript проходит именно так

Граница проведена по одному признаку: **есть ли в этом коде обращение к модели**.

- Всё, что обращается к модели — планирование, написание текста, критика, правки по findings,
  контекстные проверки — живёт в TypeScript. Там же продукт: интерфейс, API, оркестрация, SSE-
  прогресс. Mastra даёт workflow, ретраи и состояние прогона, и подключается как библиотека.
- Всё, что должно быть воспроизводимым и измеримым — разбор документа, вёрстка, экспорт, рендер,
  детерминированные проверки — живёт в Python. Там зрелая экосистема для `.pptx` (python-pptx,
  LibreOffice) и там же естественно писать код, который на одинаковом входе всегда даёт
  одинаковый выход.

Из этого следует важное практическое свойство: движок можно прогнать в тестах без GPU и без сети,
а пайплайн — на фейковом провайдере моделей с записанными ответами. Деление аудита на
детерминированную и контекстную половины — прямое следствие этой же границы, а не отдельное
решение. Детерминированные проверки над SlideIR при этом живут в TypeScript, в общем пакете: модели
они не вызывают, с `.pptx` не работают, а редактору нужны без сети (запись от 2026-09-26 в
`docs/DECISIONS.md`).

Обратное направление тоже запрещено: в TypeScript нет работы с `.pptx`. Если бы она там
появилась, вёрстка перестала бы быть детерминированной и воспроизводимой.

### 2.5. Контракты и кодогенерация

Источник правды — Zod-схемы в `packages/contracts`. Цепочка: Zod → JSON Schema
(`packages/contracts/schema/`) → Pydantic (`engine/src/engine/contracts/_generated.py`).
Сгенерированные файлы коммитятся, в CI есть шаг, который прогоняет `yarn codegen` и падает, если
появились изменения. На границе TypeScript и Python ответы движка валидируются схемами, поэтому
расхождение контрактов ломается громко и сразу.

Кодогенерация проверяет только то, что Pydantic-модели собраны из тех же схем. Что обе стороны
одинаково их **понимают**, проверяют общие фикстуры в `packages/contracts/fixtures`: один и тот
же JSON прогоняется через Zod в vitest и через сгенерированные модели в pytest. Рядом лежат
golden-фикстуры — настоящий вывод парсера на сгенерированных тестовых шаблонах, записанный
командой `uv run write-golden-ir`. Они ловят обратное направление: изменение в том, что движок
выдаёт, приходит на ревью диффом, а не обнаруживается теми, кто этот вывод читает.

Все контракты версионированы полем `schemaVersion`. Несовместимое изменение — убрали поле,
ужесточили правило, подняли версию — перестаёт принимать зафиксированные фикстуры, и CI краснеет.
Чтобы его починить, нужно описать новую версию явно, что и требуется.

### 2.6. Воспроизводимость прогона

Каждый прогон пишет манифест: версии агентов и промптов (с хешем инструкции), модели с
ревизиями, seed. Конфиг прогона (`configs/run.example.yaml`) плюс манифест однозначно описывают,
что и чем было сделано. `@lct/run-store` хранит жизненный цикл прогонов и метаданные артефактов
в PostgreSQL. Схема развивается версионированными SQL-миграциями, а допустимые переходы
`queued → running → done | failed` дополнительно защищены ограничением на уровне базы.

Бинарные входы и результаты не кладутся в PostgreSQL: локальный запуск хранит их в
`runs/<run-id>/`, а таблица `artifacts` содержит только ключ хранения, размер и контрольную сумму.
Так база остаётся источником правды для состояния, не превращаясь в blob storage. PostgreSQL и
каталог `runs/` поднимаются вместе с остальным стеком через Docker Compose и сохраняются между
перезапусками.

#### Lifecycle и progress

`@lct/run-store` ведёт единственный журнал typed-событий `JobEvent`: последовательность начинается
с нуля, не имеет пропусков и проверяется как в memory-реализации, так и в PostgreSQL. Lifecycle
переводит run из `queued` в `running`, записывает фактические start/progress/finish события этапов,
пишет валидированный `runs/<run-id>/manifest.json` при успехе и `failure.json` с диагностикой при
ошибке, затем ставит terminal state `done` или `failed`. API читает этот журнал через
`GET /runs/:runId/events?after=<seq>`; это cursor polling, не resumable SSE. Конкретные handlers
этапов подключает end-to-end orchestrator, чтобы lifecycle не имитировал несуществующую генерацию.

### 2.7. Производительность

Анализ входного контента и нового пользовательского шаблона выполняется до timed generation
stage. После отправки пользователем запроса генерации все три варианта, их аудит и обязательные
артефакты должны быть готовы не позднее чем через 5 минут. Этому служат: один plan на все
варианты, параллельные обращения к моделям по слайдам, кеширование профиля шаблона и
детерминированная вёрстка без обращений к модели. Измерение и тайминги хранятся в manifest.

Измеренные тайминги по этапам хранятся в манифестах прогонов (`runs/<run-id>/manifest.json`);
сводка по трём вариантам на шаблонах организаторов — в `docs/EVIDENCE.md` и `docs/GENERATION.md`
(23–35 с на все три варианта; это технические замеры, не SLA).

### 2.8. Чат с агентом

Разговор ведёт агент `chat-assistant` на сервере; вкладка только отправляет ход и показывает
ответ. Контракты — `packages/contracts/src/chat.ts`.

- **Ход.** `POST /chats/:id/turns` принимает сообщение, ответ на вопрос агента или одобренный
  план и отвечает потоком событий (SSE): сообщение целиком, часть ответа, кусок текста. Ход
  живёт в процессе API и не прерывается, если вкладку закрыли; `GET /chats/:id/stream`
  досматривает его после перезагрузки. Чат хранится целиком в `chats.messages`.
- **Цикл агента** (`@lct/pipeline`, `chat/`): модель отвечает текстом и вызовами инструментов
  через `tools` OpenAI-совместимого API; результаты возвращаются модели, пока она не ответит
  без инструмента, инструмент не станет ждать человека или не кончатся шаги. Сервер без
  function calling спрашивается в JSON-режиме тем же набором инструментов.
- **Инструменты** (`apps/api/src/chats/chat-tools.ts`) читают шаблоны, материалы, колоды и их
  аудит, задают вопрос, показывают план и собирают колоду через `GenerationService` — ту же
  сборку, что и `POST /generation`. Описания инструментов для модели лежат в реестре рядом с
  агентом.
- **Рекомендация варианта.** Агент и карточка результата используют сохранённый аудит сборки
  из `result.reviews`: сначала сравнивают ошибки, затем замечания, при равенстве выбирают
  сбалансированный. Браузер не подменяет эти числа живым аудитом импортированных слайдов:
  у редактора другой набор проверок. Если полного аудита нет, рекомендация явно помечается
  как выбор по умолчанию; неизвестные числа не считаются нулём.
- **Загрузка результата в чате.** Карточка читает `GET /generation/:id/summary` из сохранённого
  `deck.json` и показывает готовые PNG-превью, не ожидая повторного разбора PPTX движком.
  Запросы ограничены 20 секундами; сбой одного варианта оставляет остальные доступными,
  а неудачную загрузку можно повторить. Для просмотра, экспорта и редактора полный SlideIR
  по-прежнему загружается через `GET /generation/:id/deck` в отдельный кеш.
- **Правка объекта** (`edit_slide`). Человек прикрепляет объекты слайда из редактора (вложение
  `slides` несёт их `elementId` и текст), агент присылает новый текст частью `slide-edit`.
  Сервер принимает правку только прикреплённого текстового объекта. Черновик колоды живёт в
  браузере, поэтому пишет её редактор: карточка правки отдаёт текст журналу правок
  (`set-text`, абзацы сохраняют оформление через `paragraphsForText`), и человек отменяет её
  Ctrl+Z. Правка применяется один раз и только пока объект говорит то, что видел агент; иначе
  ждёт кнопки «Применить всё равно».
- **Режимы.** «Чат» — разговор, чтение и правка прикреплённых объектов. «План» — агент показывает план колоды
  (`DeckOutline`), человек правит и одобряет его, одобренный план собирается без модели; собрать
  неодобренный план инструмент откажет. «Авто» — план и сборка без остановки.
- **План → вёрстка.** Одобренный план не привязан к шаблону: `deck-planner` получает его как
  `outline` и только раскладывает слайды по композициям шаблона, сохраняя их порядок, число и
  тезисы. Поэтому тот же план можно собрать в другом шаблоне, а время на планирование уходит
  до нажатия «Собрать».

### 2.9. Что осознанно не делаем

- Не используем PostgreSQL как blob storage: PPTX, превью и входные файлы остаются в `runs/`.
- Не смешиваем служебное состояние Mastra в продуктовые таблицы: оно остаётся в отдельном
  LibSQL-файле внутри `runs/`.
- Не используем бета-функции Mastra (file-based agents, Editor).
- Не выставляем наружу собственные маршруты Mastra: публичный контракт — это API.
- Не кладём в репозиторий датасет организаторов и чужие корпоративные шрифты.

### 2.10. Три варианта в главном пути (2026-09-28+)

`GenerationController` использует Postgres run store, реальный `generatePresentation` и typed
`EngineClient`. Каждый `POST /generation` запускает **три прогона** (`dense`, `balanced`,
`airy`) параллельно: один `deck-planner` строит `SharedPlan`, writers пишут тексты под свой
вариант плотности, `SharedIllustrations` рисует картинки один раз на бриф, детерминированный
и контекстный аудит идут по каждому варианту. Все промпты находятся в registry; planner,
writer, critic, slot-rewriter, copy-fitter — роли одной модели, template-indexer готовит
шаблон вне timed-бюджета.

`engine.api` связывает независимые `parser.compositions`, `layout.text_fit`,
`export.compositions` и `render`. `.pptx` хранит исходные layout/master/relations;
модель выбирает композиции, но не генерирует координаты. `CompositionExportRequest` и
`CompositionCheckResponse` валидируются с обеих сторон. Model-only Zod-схемы (`CompositionPlan`,
`TemplateIndex`, `CopyEdits`, промпты иллюстраций) экспортируются из contracts, но не требуют
Pydantic: они не пересекают границу Python.

Редактор открывает готовую колоду через `deck-import` (движок читает `.pptx` обратно как
SlideIR с картинками) и экспортирует правки в нативные PPTX/PDF, а PNG/HTML — из отрендеренных
превью: `POST /generation/:id/export` и `GET /generation/:id/exports/:exportId/:name`.
Подробности пути — в `docs/GENERATION.md`.

## 3. Генерация презентации

[↑ к оглавлению](#оглавление)

Рабочий путь в `main` на 29 сентября 2026: один бриф раскладывается **тремя вариантами**
(`dense`, `balanced`, `airy`) параллельными прогонами с общим планом, аудитом, PPTX/PDF/PNG и
персистентным API. Это подтверждение транспорта, экспорта и времени, а не финальной ML-оценки
качества на любом неизвестном шаблоне или production SLA.

### 3.1. Запуск

Нужны Node 22.13+, Yarn, Python 3.12/uv, LibreOffice (`soffice`), Poppler (`pdftoppm`)
и fontconfig (`fc-match`). Шрифты выбранного шаблона нужны, чтобы превью совпало с
файлом; без них колода всё равно собирается. Dockerfile движка устанавливает
инструменты и Play с SIL OFL. На macOS шрифты из `infra/fonts/Play` нужно установить в
`~/Library/Fonts`; движок создаёт отдельный fontconfig для headless LibreOffice.

В игнорируемом `.env` задаются `MODEL_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` из `.env.example`.
Не сохранять ключи в исходниках, run manifests, документации и shell history.

```bash
yarn install --immutable
uv sync
yarn nx run-many -t build -p pipeline,engine-client
uv run uvicorn engine.api:app --host 127.0.0.1 --port 8000
# В другом терминале:
node --env-file=.env --import tsx scripts/generate-presentation.mts \
  /absolute/path/template.pptx /absolute/path/brief.md 10
```

CLI сначала подготавливает профиль, затем запускает измеряемую генерацию. Результат —
`runs/<uuid>/deck.pptx`, `previews/deck.pdf`, PNG всех слайдов, `plan.json`, `deck.json`,
`audit.json`, `images.json`, `events.jsonl`, `manifest.json`. При отказе записывается
`failure.json`; незавершённая работа не объявляется готовой.

API и CLI можно гонять и по конфигу прогона (`configs/run.example.yaml`): `lct generate
<config.yaml>` строит план один раз, раскладывает его перечисленными в конфиге вариантами
(от 1 до 3), прогоняет детерминированный и контекстный аудит и пишет в `runs/<run-id>/`
план, слайды, аудит и `manifest.json` каждого варианта.

### 3.2. Почему используется исходный шаблон

Docker-движок содержит оригинальные Play и Inter (включая Inter SemiBold). Для других
гарнитур задайте `TEMPLATE_FONTS_DIR` в `.env`: каталог монтируется только для чтения,
а стартовый скрипт обновляет fontconfig до запуска HTTP-сервера. По умолчанию это
игнорируемый `data/fonts`. На текущем macOS-хосте четыре начертания Arial скопированы
из системного каталога в `data/fonts`; они исключены из Git и Docker build context.
Прямой mount `/System` запрещён настройками Docker Desktop. После изменения каталога:
`docker compose up -d --force-recreate engine`. Если исходной гарнитуры нет, сборка
продолжается: в `.pptx` остаётся её имя, превью LibreOffice рисует заменой, а ответ
движка (`missingFonts` и `warnings`) и ход прогона сообщают об этом. Подробнее —
`infra/fonts/README.md`.

Временный каталог рендера создаётся внутри каталога результата. Поэтому публикация
PDF/PNG через атомарный rename не пересекает файловые системы контейнера и bind mount
`runs/` (раньше этот случай приводил к `EXDEV: Invalid cross-device link`).
Проверка 2026-09-27 через Docker API: Shablon_PROD, 10 слайдов — 16.150 с; VK Education,
10 слайдов — 12.203 с до состояния done и готовых артефактов. Скачивание PPTX/PDF,
контрольные суммы и persisted listing проверены. Это техническая проверка, не ML-оценка
качества; во втором прогоне сохранено замечание критика к пустому полю на слайде 7.

Python извлекает композиции реальных слайдов и наследование placeholder → layout → master.
В профиль попадают шрифты, кегли, границы, внутренние поля, межстрочные интервалы и ёмкость.
Экспорт клонирует выбранные моделью слайды внутри исходного PPTX и заменяет нативный текст,
не пересобирая брендинг по приблизительной палитре. Сохраняются фон, тема, мастер-макеты,
расположение, интервалы и существующий декор. В TypeScript нет разбора или изменения PPTX.

Профиль не даёт модели произвольных координат: модель выбирает подходящие исходные композиции,
их порядок и содержание. Это минимальный безопасный путь к первому template-faithful результату.
Свободная перестройка всех объектов и создание новых native charts/tables вне композиций
в этот режим не входят.

### 3.3. Mastra и обращения к модели

- **Подготовка (вне тайминга).** Для каждого шаблона один раз читается generation profile,
  агент `template-indexer` описывает композиции (для чего каждая, сколько элементов, какие
  страницы — reference), а библиотека получает PNG всех слайдов шаблона. Индекс кешируется в
  Postgres вместе с профилем и пересобирается, если изменился хеш шаблона или версия промпта.
  Отказ индексатора не блокирует колоду: планировщик просто работает без заметок.
- **Один planner на бриф.** `deck-planner` строит план один раз: о чём каждый слайд, какая
  композиция, какой картинки он просит. Один и тот же план (`SharedPlan`) и одни и те же
  иллюстрации (`SharedIllustrations`) используются всеми тремя вариантами.
- **Три варианта параллельно.** Каждый вариант — отдельный прогон (`generatePresentation`) со
  своим writer'ом: один и тот же план раскладывается под плотность варианта. `dense` — самые
  заполненные макеты, `balanced` — средние, `airy` — просторные; писатель получает поправку и
  перепланирует, если один макет занял больше трети колоды. `foreach` запускает writer по
  слайдам с concurrency 3.
- **JSON автора** содержит объект `textsBySlot` с обязательными ключами всех полей;
  это исключает повторные/пропущенные ID из свободного массива bindings.
- **Переполнение** передаётся slot-rewriter: он предлагает три законченные формулировки.
  Код выбирает помещающийся вариант, но не обрезает слова и не уменьшает шрифт. Отдельный
  агент `copy-fitter` укорачивает заголовки и буллеты, которые не влезли, до заданной длины,
  сохраняя факты и цифры.
- Движок проверяет длину текста по метрикам шрифта и доступным строкам, включая соседний
  текстовый блок. Проверка повторяется перед экспортом.
- Контекстный critic той же модели предлагает правки; до двух раундов repair проходят через
  отдельный Mastra workflow. Остаточные смысловые замечания сохраняются как предупреждения
  `content-review-required`, не скрываются и не приравниваются к успешной ML-оценке.
- Детерминированное переполнение блокирует экспорт. Отсутствующий выбранный шрифт также
  блокирует faithful render вместо молчаливой замены гарнитуры.
- Лимитер провайдера допускает `MODEL_MAX_CONCURRENCY` (по умолчанию 8) HTTP-запросов на
  процесс, совместно для всех прогонов; несколько процессов требуют внешнего согласования
  квоты команды 10. Deadline каждого прогона — 290 секунд, на экспорт, аудит и рендер после
  ожидания картинок резервируется минута.
- Текстовые роли используют Qwen3-30B-A3B-Instruct-2507 (30.5B, потолок кейса — 35B), зрение —
  Qwen3-VL-8B-Instruct. Thinking отключён; схемы проверяются провайдером и Zod. До трёх попыток
  при 429/502/503 или усечённом JSON. Параметры ролей читаются из `registry/agents/*/agent.yaml`.

Архитектурные точки расширения: `TextProvider` для endpoint, registry для инструкций,
`GenerationProfile` для новых свойств шаблона, `ImageProvider` для генератора изображений.

### 3.4. Иллюстрации

Слот картинки (`imageSlots` композиции) находит парсер движка: picture-плейсхолдер или большая
пустая залитая карточка, на которой ничего не нарисовано (`placeholder` и `panel`). Рамки меньше
8% площади слайда (портреты, иконки, QR) слотами не считаются. Фото и фирменный арт шаблона —
его дизайн, их не заменяем.

1. Планировщик получает `imagesAvailable` и число `imageSlots` у каждой композиции. Без модели
   изображений композиции со слотами ему не предлагаются, пока без них хватает макетов.
2. Сразу после плана (`onPlan`) начинается рисование, параллельно с написанием текста. Агент
   `illustrator` (текстовая модель) пишет промпт по `imageQuery`, утверждению слайда, аудитории и
   стилю шаблона: палитра `designSystem.palette`, тёмный или светлый фон, форма рамки. Текст,
   логотипы, водяные знаки, QR и узнаваемые лица запрещены в промпте.
3. `SharedIllustrations` рисует слот слайда один раз на бриф: три варианта с одной формой рамки
   получают одну картинку. Размер — ближайший к боксу из 1024x1024, 1536x1024, 1024x1536.
4. Перед экспортом прогон ждёт картинки, пока от бюджета 290 с не останется минута на экспорт.
   Не успевшая или не нарисованная картинка оставляет слот пустым.
5. Движок вставляет картинку нативно (`add_picture`) в бокс и геометрию слота: `cover` обрезает
   по боксу без искажения пропорций, `contain` вписывает целиком. Слот без картинки экспорт
   удаляет, так что белых прямоугольников и пустых рамок не остаётся. Проверка аудита
   `empty-image-slot` ловит рамку, оставшуюся без картинки.

`images.json` каждого варианта хранит слот, запрос, промпт, seed, размер, модель и статус
(`generated`, `failed`, `timed-out`). Картинку, которую сервер не отдал, ничем не подменяем.
Манифест пишет агента `illustrator`, модель изображений и время этапа `illustrating`.

Модель изображений берётся из роли «Иллюстратор» в настройках, иначе из `IMAGE_BASE_URL` вместе с
`IMAGE_MODEL`. `IMAGE_PROVIDER=fake` рисует однотонные картинки без сети: так проходят тесты и
офлайн-демо. Проверка 2026-09-29, шаблон ЦУ, `IMAGE_PROVIDER=fake`: три варианта за 90 с, этап
иллюстраций 20–45 с, картинки в слотах обложки, фото-слайдов и рамки устройства.

### 3.5. API и сохранение

При загрузке весь PPTX разбирается в профиль, но для обложки LibreOffice экспортирует
только первую страницу, а Poppler растеризует только её. Оба процесса делят бюджет
20 секунд, меньший стандартного HTTP-таймаута движка (30 секунд). Если превью не удалось,
возвращается профиль с `previewDataUrl: null`; экспорт готовой колоды по-прежнему рендерит
все слайды. Ошибки движка при загрузке получают понятные статусы 422/503/504,
а интерфейс показывает сообщение API. Это не гарантирует загрузку произвольно большого
файла за 30 секунд: сам парсинг и передача данных тоже занимают время.

Регрессионная проверка 2026-09-27: внешний шаблон ЦУ, 166 слайдов, 49 208 895 байт.
До исправления Docker API возвращал 500 через 30.444 секунды; после — 202 за 10.289
секунды с валидным профилем всех 166 слайдов и PNG обложки. Профиль и превью подтверждены
через сохранённый список шаблонов. Это измерение загрузки, не генерации новой колоды.

1. `POST /files/template` с multipart `file`: сохранение и исходный разбор.
2. `POST /generation/prepare` с `{templateId}`: generation profile в Postgres, индекс композиций
   и отрисовка слайдов шаблона для библиотеки. `GET /generation/prepare/:templateId` показывает
   ход подготовки.
3. `POST /generation` с `{templateId, brief, slideCount?, outline?, contentIds?, projectId?, seed?, model?}`:
   сервис запускает **три прогона сразу** (`dense`, `balanced`, `airy`) с общим планом;
   `model` — `{connectionId, modelId}` из настроек моделей, без него — модель роли writer или
   подключение из `.env`. Каждый вариант — отдельный `run-*` с событиями и артефактами,
   библиотека показывает один build.
4. `GET /runs/:id` и `GET /runs/:id/events?after=N`: сохранённое состояние/прогресс.
5. `GET /generation/:id/deck` — колода для редактора: слайды, прочитанные движком из готового
   `.pptx`, с картинками из `media/`; `GET /generation/:id/previews` — PNG слайдов;
   `GET /generation/:id/artifacts/deck.pptx | deck.pdf | slides.zip | manifest.json | slide-N.png`.
6. `POST /generation/:id/export` — экспорт отредактированной колоды: нативные PPTX и PDF, а для
   PNG и HTML — отрендеренные превью; `GET /generation/:id/exports/:exportId/:name` отдаёт файл.
7. `PATCH /generation/:id` (название, проект) и `DELETE /generation/:id` (весь build).
8. `GET /generation` — завершённые колоды после повторного открытия, по одной на build.

Все маршруты, кроме `GET /health`, требуют заголовок `x-lct-service-token` со значением
`API_SERVICE_TOKEN`: API отвечает только веб-серверу. Браузер ходит через `/api/backend/...`
веб-сервера, который проверяет сессию и добавляет токен. Колоды и шаблоны принадлежат
аккаунту, загрузившему их: чужой объект отвечается как отсутствующий.

Повторяемый live smoke для уже загруженного шаблона:

```bash
API_URL=http://localhost:3001 API_SERVICE_TOKEN=... node --import tsx scripts/smoke-generation-api.mts \
  TEMPLATE_UUID /absolute/path/brief.md 10
```

Smoke проверяет state `done`, число слайдов, скачивание обоих файлов, совпадение SHA-256 с
manifest и наличие колоды в persisted listing. Ключ нужен только API, не браузеру.

### 3.7. Проверки и ограничения

Offline tests не обращаются к Yandex. Проверяются ограниченная параллельность, JSON, отмена,
лимитер, repair/failure, публикация артефактов, наследование шрифта, геометрия, переполнение,
соседние блоки и missing-font gate. Проверки проекта: Nx tests/typecheck/lint/build,
pytest, Ruff, Pyright, import-linter, воспроизводимость codegen.

Ограничения текущего режима:

- три варианта запускаются всегда (конкурсный gate); CLI-конфиг позволяет запросить 1–3;
- вход для генерации — brief и txt/md/csv/tsv, не полноценный PDF/DOCX/XLSX content adapter;
- charts/tables рисуются нативными объектами внутри выбранных композиций; ряд
  reference/неизменяемых растровых страниц planner не предлагает;
- если шрифта шаблона нет на сервере, `.pptx` сохраняет его имя, а превью рисуется заменой и помечается предупреждением; установка шрифта внутрь файла не реализована;
- контекстный аудит — предварительная помощь, окончательное качество оценивает ML-команда;
- редактор открывает готовую колоду и экспортирует правки в PPTX/PDF/PNG/HTML, но импорт
  произвольного пользовательского PPTX в редактор и полный round-trip всех свойств
  (объединение ячеек, коннекторы, сложные эффекты) не реализованы;
- PDF и PPTX экспортируются движком; PNG — архивом превью, HTML — страницей, собранной на
  клиенте из PNG-превью; hosted `latest` не гарантирует воспроизводимость весов или побитовую
  повторяемость;
- прерывание HTTP к движку не гарантирует немедленную остановку уже начатого LibreOffice;
- clean-clone Docker runtime не подтверждён этой проверкой.

Итоговая проверка: 48 Nx targets (tests/typecheck/lint/build) для 12 проектов прошли;
182 Python tests; Ruff, Pyright и три import-linter contracts прошли; повторный codegen
стабилен, `git diff --check` без ошибок. Нативный текст всех 10 слайдов повторно прочитан
из PPTX и сверен с планом. PowerPoint UI не использовался; визуальная проверка — LibreOffice/PNG.

При визуальном просмотре последнего API-прогона также видны повторы нескольких ролей и
слишком короткие подписи на отдельных карточках. Это не overflow, но недостаток содержательного
качества. Поэтому готовность real-model transport/export и выполнение времени отделены от
окончательной приёмки качества; последняя остаётся за ML-оценкой и дальнейшей настройкой.

## 4. Модели

[↑ к оглавлению](#оглавление)

Каталог моделей живёт в `configs/models.yaml`: прогон ссылается на записи по id, а манифест
прогона фиксирует разрешённую ревизию, чтобы колоду можно было связать с конкретными весами.

Все обращения к моделям происходят на стороне TypeScript, в `packages/pipeline`. Движок моделей
не вызывает вообще — это позволяет прогонять его тесты без GPU и без сети.

### 4.1. Активное подключение

Текстовые роли читают `planner-default`, `writer-default` и `critic-default`: это
Qwen3-30B-A3B-Instruct-2507, 30.5B параметров и около 3.3B активных на токен. Картинки слайдов
читает `vision-default`, Qwen3-VL-8B-Instruct, 8.8B. Обе модели открытые, Apache-2.0, и обе ниже
потолка кейса в 35B. Qwen3.6-35B-A3B (около 35.95B по metadata весов) в каталоге нет: базовый
инстанс Yandex AI Studio отдаёт именно её под именем `qwen3.6-35b-a3b`, поэтому этот URI в
`.env` ставить нельзя.

**Демостенд** (https://lct-demo.awenylab.com, 2026-09-29) работает на `qwen3.6-35b-a3b` из Yandex
AI Studio для всех текстовых ролей. Qwen3-30B-A3B-Instruct-2507 в AI Studio нет, а единственная
меньшая открытая модель там, `gpt-oss-20b` (Apache-2.0, 21B), на проверке собрала три варианта
за 5 мин 20 с, за пределами бюджета; Qwen3.6-35B-A3B укладывается в 3 минуты. Модель —
Apache-2.0, её класс по названию — 35B (по metadata весов 35.95B, см. «Потолок 35B»).
Иллюстрации на стенде выключены: ни одна доступная нам модель изображений не открытая; роль
«Иллюстратор» подключается в настройках любой OpenAI-совместимой text-to-image моделью.

Endpoint и имя модели задаются только окружением:

- `LLM_BASE_URL` — OpenAI-совместимый runtime с весами `Qwen/Qwen3-30B-A3B-Instruct-2507`;
- `LLM_MODEL` — имя, под которым runtime их отдаёт; пустое значение значит имя репозитория из каталога;
- `VLM_BASE_URL` и `VLM_MODEL` — то же для `Qwen/Qwen3-VL-8B-Instruct`;
- `MODEL_API_KEY` — секрет в локальном `.env`, заголовок `Authorization: Bearer ...`.

API и CLI используют один `OpenAICompatibleProvider`; автоматического переключения на
OpenRouter или другую модель нет. Каждый запрос передаёт
`chat_template_kwargs: { enable_thinking: false }` и `response_format` типа `json_schema`
со строгой схемой, полученной из Zod. Ответ дополнительно валидируется локально.

Общая квота каталога, сообщённая командой, — 10 одновременных запросов. Приложение занимает
`MODEL_MAX_CONCURRENCY` (по умолчанию 8) HTTP-слотов **на процесс**, совместно для всех прогонов;
трём вариантам одной генерации этого хватает, чтобы идти параллельно. CLI и несколько API replicas
имеют независимые лимитеры: параллельные процессы необходимо учитывать при распределении
общей квоты. При 429/502/503 разрешены максимум две повторные попытки с backoff; ожидание
очереди и backoff прерываются общим сигналом отмены/deadline. Ключи и тела ошибок провайдера
не включаются в сообщения ошибок приложения.

### 4.2. Подключения из интерфейса и ключи

Кроме подключения из `.env`, модели подключают в интерфейсе («Настройки → Модели»). Прогон
получает от браузера только выбор `{connectionId, modelId}`; модель берётся так: выбранная у поля
ввода, иначе модель роли `writer`, иначе подключение из `.env`. Нет ни одной — API не создаёт
прогон и отвечает 503 с понятной причиной.

- **Подключение из `.env`** видно в интерфейсе как встроенное (`connectionId: server`): его можно
  проверить, но не изменить и не удалить. Ключ правят в `.env`, в браузер уходят только признак
  ключа и его последние четыре символа.
- **Ключи подключений из интерфейса** хранит API в Postgres (`model_connections`) только
  шифротекстом AES-256-GCM. Ключ шифрования выводится из `MODEL_KEYS_SECRET`, который
  `lct onboard` генерирует один раз на установку; id подключения входит в аутентифицированные
  данные, так что шифротекст, перенесённый в другую строку, не расшифруется. Без секрета ключ не
  сохраняется совсем. Ключ, который перестал расшифровываться, интерфейс показывает как
  незаданный — его вводят заново.
- **Ни один ответ API не содержит ключа**: наружу уходит только публичный вид подключения
  (`modelConnectionSchema`), в журнал `model_settings_events` — кто и что изменил, без ключа.
- **API отвечает только веб-серверу**: запрос без `API_SERVICE_TOKEN` получает 403, открыт только
  `/health`. Настройки моделей доступны лишь серверным действиям веба; прокси `/api/backend` для
  браузера их не пропускает.
- **Адрес, куда API идёт с ключом**, проверяется: редиректы запрещены (`redirect: 'error'`), чтобы
  ключ не ушёл на чужой хост, а адреса внутренних сетей (loopback, 10/8, 172.16/12, 192.168/16,
  169.254/16, ULA IPv6) запрещены, пока `MODEL_ALLOW_PRIVATE_HOSTS` не равен `true`. Имя хоста
  сначала разрешается, так что публичное имя с частным адресом тоже ловится. Подключение из `.env`
  задаёт администратор, на него запрет не распространяется.

Список у поля ввода можно сузить по семейству, а в выборе модели для роли длинный список
подключения разложен по семействам подменю. Семейство читается из id модели по обычному
имени (GPT, Claude, Gemini, Qwen, Llama, DeepSeek, Mistral, Grok, Command, Phi, Gemma, Yi),
а не по возможностям: проверка подключения отдаёт только id. Префикс протокола семейством
не считается, поэтому `gpt://.../qwen3` остаётся Qwen.

У подключения можно оставить только часть найденных моделей (меню подключения → «Модели»,
там же «Включить все» и «Выключить все» — для всего списка или для отфильтрованного).
Выключение — свойство подключения, а не аккаунта: у общего подключения и подключения из
`.env` оно действует для всех, кто пользуется этим ключом, и меняет его только
администратор. Выключенная модель пропадает из выбора у поля ввода и у ролей, а сервер
отклоняет прогон с ней. Пока ничего не выключено, доступна любая модель, и новые тоже;
как только часть выключена, доступны только включённые — вписать id вручную у такого
подключения нельзя, иначе так обходили бы запрет. Неудачная проверка список не сбрасывает.
Список подключения из `.env` хранится в базе по его адресу, поэтому переживает перезапуск,
а другой адрес в `.env` начинает без ограничений.

Иллюстрации рисует роль `image` через OpenAI-совместимый `POST /images/generations`
(`OpenAICompatibleImageProvider`): просит `b64_json`, принимает и `url`, повторяет при 429, 502,
503 и обрыве сети, одна картинка ждёт не дольше 90 с. Картинки идут через свой пул
(`IMAGE_MAX_CONCURRENCY`, по умолчанию 3) и не занимают слоты текстовой модели. Промпт пишет
агент `illustrator` на модели писателя. Порядок выбора модели и запасной путь без неё описаны
в `docs/GENERATION.md`, раздел «Иллюстрации».

`latest` — изменяемый provider alias, а не зафиксированный commit весов. Манифест честно
указывает `hosted-revision-not-reported`; hash URI не является checksum весов.

Проверка 2026-09-27: обычный текст и строгий JSON вернули HTTP 200 за 0.81 и 0.21 секунды.
Живой Mastra workflow (план + два writer-запроса) завершился за 1056 мс. Evidence без секретов:
`runs/provider-check/yandex-result.json`. Это небольшой smoke-тест, не доказательство
готовности PPTX или выполнения полного пяти-минутного SLA.

### 4.5. Как модель вызывается

- Провайдер `openai-compatible` говорит с любым рантаймом с OpenAI chat API: vLLM, llama.cpp,
  SGLang или внешний провайдер моделей с открытыми весами. Адрес берётся из переменной
  `baseUrlEnv` записи каталога, ключ из `MODEL_API_KEY`, имя модели из `servedName` или `repo`.
- Инструкция агента из `registry/agents/<id>/instructions.md` уходит системным сообщением, вход
  шага пользовательским сообщением в JSON, параметры генерации из `agent.yaml`, seed прогона.
- Ответ обязан быть JSON схемы `outputSchema` агента. Невалидный ответ отправляется модели
  обратно один раз вместе с ошибкой валидации, после второй неудачи шаг падает: ограниченный
  повтор держит прогон в бюджете времени.
- `MODEL_PROVIDER=fake` отвечает записанными ответами, без сети и GPU: так работают тесты и
  офлайн-демо. `MODEL_PROVIDER=record` вызывает настоящую модель и записывает ответы.

### 4.6. Требования к выбору весов

- **Лицензия.** Веса берём только под лицензиями, которые допускают коммерческое использование:
  та же политика, что и для зависимостей (см. `docs/LICENSES.md`). Лицензия каждой записи
  указывается в `configs/models.yaml` и попадает в эту таблицу.
- **Ревизия.** В конфиге фиксируется коммит или тег, а не `main`: иначе прогон перестаёт быть
  воспроизводимым.
- **Доступ.** Модели обслуживаются рантаймом с OpenAI-совместимым API, адрес берётся из
  переменной окружения, указанной в поле `baseUrlEnv`. Ключи в репозиторий не попадают.
- **Веса в репозиторий не коммитятся.** В нём есть только ссылки и ревизии.

### 4.7. Системные требования

Раздел заполняется после замеров: сюда приходят требования по видеопамяти и по времени ответа на
слайд, из которых складывается общий бюджет в 5 минут на генерацию всех трёх вариантов после
отправки пользователем запроса. Анализ шаблона и входного контента измеряется отдельно как
подготовительный этап.

### 4.8. Потолок 35B

Кейс разрешает открытые веса не больше 35B параметров. Qwen3.6-35B-A3B по metadata содержит
35 951 822 704 параметра, около 35.95B, поэтому каталог на неё не ссылается. Текстовые роли
сидят на Qwen3-30B-A3B-Instruct-2507 (safetensors: 30 532 122 624, 30.5B), ревизия
`0d7cf23991f47feeb3a57ecb4c9cee8ea4a17bfe`. Зрение — Qwen3-VL-8B-Instruct (8 767 123 696, 8.8B),
ревизия `0c351dd01ed87e9c1b53cbc748cba10e6187ff3b`. Иллюстрации рисует роль `image`, см. выше.

## 8. Журнал решений

[↑ к оглавлению](#оглавление)

Здесь живут только архитектурные инварианты: решения, которые нельзя вывести из кода за минуту и
отмена которых заденет больше одного пакета.

Версии зависимостей, выбор библиотек и настройки инструментов сюда не пишем — им место в
комментарии рядом с самой настройкой или в разделе «Грабли» в `CONTRIBUTING.md`. Тот, кто полезет
менять версию, увидит комментарий в файле; запись в этом журнале он не увидит никогда.

Записи не редактируем и не удаляем. Решение изменилось — добавляем новую и ссылаемся на старую.

### 8.1. 2026-09-18. Граница между Python и TypeScript: по наличию вызова модели

Всё, что обращается к модели, живёт в TypeScript; всё, что должно быть детерминированным и
воспроизводимым — разбор `.pptx`, вёрстка, экспорт, рендер, измеримые проверки — живёт в Python.
Отсюда же деление аудита на контекстную и детерминированную половины и возможность прогонять
тесты движка без GPU и без сети. Правило закреплено машинно: `@nx/enforce-module-boundaries` на
стороне TypeScript, import-linter на стороне Python.

### 8.2. 2026-09-18. Слои движка независимы, соединяет их только API

`parser`, `layout`, `visuals`, `export`, `render` и `checks` не импортируют друг друга и знают
только `engine.contracts`; `engine.api` стоит над ними. Описано контрактами import-linter в
`engine/pyproject.toml`. Мотив — менять вёрстку, не задевая парсер, и тестировать слои по
отдельности.

### 8.3. 2026-09-18. Контракты: Zod: источник правды, Pydantic генерируется

Схемы описываются один раз в `packages/contracts`, из них собирается JSON Schema, из неё —
Pydantic-модели движка. Сгенерированные файлы коммитятся, CI перегенерирует их и падает на любом
расхождении. Альтернатива — держать два описания руками — разъезжается на второй неделе.

### 8.4. 2026-09-18. Состояние без базы данных

Отдельная СУБД не заводится: результаты прогонов лежат в `runs/`, состояние Mastra — в
LibSQL-файле там же. Это снимает с демо-стенда лишний сервис и делает прогон переносимым вместе с
каталогом.

### 8.5. 2026-09-18. Профиль шаблона вместо любых условий по шаблону

Ни в коде, ни в конфигах не бывает ветвлений вида «если шаблон такой-то», зашитых названий
макетов, цветов, шрифтов и координат. Всё, что зависит от шаблона, читается из профиля шаблона.
На защите дадут незнакомый шаблон, и сценарий `eval/unknown-template.yaml` существует ровно для
того, чтобы это проверять.

### 8.6. 2026-09-18. Apache 2.0 и исполняемая политика лицензий

Решение открытое, заказчик говорит о пилоте и внедрении, поэтому выбрана Apache License 2.0 — она
даёт явную патентную оговорку. Зависимости допускаются только под разрешительными и слабыми
копилефт-лицензиями; GPL и AGPL не подходят. Политика не декларативная: `yarn licenses` обходит
дерево обеих экосистем и падает, если в нём появился копилефт.

### 8.7. 2026-09-22. Редактор пишет свойства объектов в SlideIR, журнал правок остаётся аудит-трейлом

Заливка, обводка, форма, поворот, прозрачность, блокировка, выравнивание текста и фон слайда —
необязательные поля `SlideIR` (`schemaVersion` остаётся 1: старые полезные нагрузки по-прежнему
проходят схему). Источник правды для экспорта — итоговый `SlideIR` из редактора, а не поток
`PatchOp`: операций вставки, дублирования, порядка слоёв и правки данных таблиц и графиков в
`FixPatch` нет и не появится, там остаются только правки, которые движок умеет применить сам.
`PatchOp` редактор продолжает записывать там, где операция существует (`move`, `set-text`,
`set-font-size`, `set-color`, `remove`), и это аудит-трейл: по нему видно, что и чем меняли.

Альтернатива — довести `FixPatch` до полного набора операций редактора — означала бы вторую
реализацию редактора на стороне движка и новую версию контракта при каждой новой кнопке.

Следствия: `engine.export` берёт слайд целиком; `@lct/deck-ops` заполняет `ops` только там, где
операция есть, а в остальных изменениях оставляет пустой список; при сериализации `SlideIR` на
стороне Python отсутствующее поле и `null` значат разное (`fill: null` — «без заливки», ключа нет
— «шаблон не сказал»), поэтому дамп делается с `exclude_unset`.

### 8.8. 2026-09-26. Проверки над SlideIR: в TypeScript, живым аудитом в редакторе

Уточняет запись от 2026-09-18 о границе Python и TypeScript. Детерминированные проверки, которым
хватает `SlideIR` и профиля шаблона, — переполнение, наложение, выход за край и поля, заглушки,
контраст, отсутствующие шрифты, — живут в `packages/slide-audit` (`scope:shared`). Редактор
запускает их в браузере после каждой правки, как линтер в редакторе кода; пайплайн — после вёрстки,
теми же функциями. В `engine.checks` остаются проверки, которым нужен сам файл `.pptx` или его
рендер. Граница «в Python нет вызова модели, в TypeScript нет работы с `.pptx`» не меняется:
пакет читает `SlideIR` и ни одной модели не вызывает.

Мотив — живой аудит. Движок доступен фронту только через API, так что проверка на каждое движение
объекта шла бы по сети и без сервера не работала бы. К тому же переполнение точнее меряется в
браузере: там загружены сами шрифты, а у движка их может не быть. Отдельная ML-модель для
наложений и переполнения отклонена: это задачи с точным ответом, размеченных данных нет, а
находка обязана показывать измеренное число и порог.

Следствия:

- Два уровня — ошибка (ломает слайд или файл) и предупреждение; на шкалу контракта они
  ложатся как `blocker` и `minor`.
- «Исправить» — только геометрия без модели: ближайшее свободное место в полях шаблона, иначе
  исправления нет. Смысловые правки — сократить текст, сменить макет — делает агент, и его правку
  проверяет тот же аудит.
- Реестр проверок — `packages/slide-audit/src/checks.json`, `docs/AUDIT.md` генерируется и из
  него.
- Пропущенные находки пока хранятся только в браузере: места для них в контракте колоды нет.

### 8.9. 2026-09-28. Три варианта: параллельные прогоны с одним планом

Один `POST /generation` запускает три прогона (`dense`, `balanced`, `airy`) сразу: каждый
вариант — отдельный `run-*` со своими событиями, аудитом и артефактами, но все три делят один
план (`SharedPlan`) и одни иллюстрации (`SharedIllustrations`). Ось различий — плотность:
варианты выбирают разные композиции шаблона и по-разному укладывают текст, но не меняют факты.
Пользователь видит один build, библиотека хранит его как одну колоду.

Альтернатива — один прогон с тремя вёрстками внутри — означала бы общий файл прогресса, общий
аудит и невозможность перезапустить один вариант без остальных; детерминированный путь движка
(`POST /v1/layouts`) для этого всё равно существует. Отмена решения затрагивает контракт
генерации, `GenerationService`, `generatePresentation` и CLI.

### 8.10. 2026-09-29. Картинки рисуются один раз на бриф, слот без картинки убирается

Иллюстрации генерирует TypeScript (`SharedIllustrations`) сразу после плана, одну на слот слайда
для всех трёх вариантов, параллельно с текстом. Движок получает готовый файл под `media/` прогона
и вставляет его нативно в бокс слота, не зная, откуда он взялся. Слот картинки — только
picture-плейсхолдер или большая пустая карточка шаблона; фото и арт шаблона остаются его дизайном.

Слот, для которого картинки нет (модель не назначена, сервер не ответил, не успели в бюджет),
экспорт удаляет, а планировщик без модели изображений такие композиции не получает. Пустая рамка
на слайде хуже, чем её отсутствие: она выглядит как незаконченная работа. Отмена этого решения
затрагивает контракт композиции, парсер и экспорт движка, пайплайн и планировщика.
