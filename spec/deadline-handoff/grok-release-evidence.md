# Grok: эксплуатационная приёмка и оставшиеся требования UltraReview

Самостоятельное задание на код и проверяемые результаты. Репозиторий:
https://github.com/TheAweny/case-14-ai-presentation-designer-team-41.
База — актуальная `theaweny/generation-deadline-integration`, либо main после её слияния.
Начинай этот пакет после интеграции пакета изображений/экспорта, чтобы не проверять старый SHA.
Создай ветку `theaweny/grok-release-evidence`; commit, push и PR разрешены. Не deploy и не merge
в main без отдельного поручения. Локальные вложения и история чата не нужны.

## Цель и уже принятые решения

Довести сервис до честной приёмки полного UltraReview: качественные три варианта, bounded
расходы/попытки, восстановление без повторения подтверждённой работы, объяснимые ошибки и
реальные артефакты. Зелёный CI/CD не доказывает успешную генерацию.
Корпоративный продукт: аккаунты создаёт администратор; открытая регистрация не требуется.
Пользовательские ограничения опциональны и выключены по умолчанию. Считаются успешные
пользовательские операции/генерации, параллельность и хранение; обязательный денежный баланс
не нужен. Три варианта — одна генерация. Failed/partial/cancel не списывают успешную генерацию,
resume идемпотентен. Личные ключи учитываются отдельно, инфраструктурные ограничения остаются,
автоматического перехода на общий платный ключ нет. Телефонный редактор не исправлять.

Прочитай AGENTS.md, docs/ARCHITECTURE.md и docs/GENERATION-RECOVERY.md. Уже реализованы
immutable spec, task checkpoints, lease/fencing, retry варианта, usage ledger, editor snapshots,
конфликты и экспорт revision. Новая база добавляет readiness индекса, пределы content stage,
typed datasets и проверку связей чисел, текущие снимки в inspection tools. Не переписывай их.

## Пакет работ

1. Проверь общий provider boundary, а не по одному modelId: concurrency, RPM/TPM и квоты
   могут быть общими для endpoint/account. Сохрани существующий потолок. Найди и устрани
   перемножение retries provider/workflow/tool. Retry-After, bounded jitter/backoff, отменяемая
   очередь, fairness для чата и соседних сборок, отсутствие retry storm. Сделай минимально
   необходимую координацию для реально поддерживаемого числа API workers; если кластер
   не поддержан, честно зафиксируй это и не имитируй распределённый scheduler.
2. Fault matrix на настоящем API/engine/БД с fake provider: остановка после 7-го слайда;
   restart API; два resume одновременно; stale worker; разрыв SSE отдельно от Stop;
   crash между provider response/checkpoint, file write/DB commit, export/publication;
   ошибка экспорта только одного варианта. Успешные task outputs не вызываются снова,
   stale callback не меняет новую revision, отменённое само не возобновляется. Unknown
   внешнего запроса не означает нулевую стоимость и не даёт гарантии exactly-once billing.
3. Проверь ledger всех ролей и транспортов: logical task/HTTP attempt, streaming failures,
   compatibility fallback, cached/reasoning tokens, vision/images, failed/unknown charges,
   cumulative resume usage. Не привязывай учёт к конкретному instanceof. UI различает ошибки
   provider/auth/429/timeout/content/export/persistence и выводит русские действия восстановления.
4. Проверь опциональные account limits: админ включает/выключает, успешная тройка считает один,
   ошибки/partial/cancel не тратят успехи, конкурирующие старты не обходят лимит, stale reservation
   освобождается без чужого списания, storage сохраняет редактор и export. Не вводи новый paywall.
5. Материалы: исследование PDF/DOCX/XLSX должно маршрутизироваться к подготовленному тексту
   и typed таблицам с pagination/hash/source coordinates. Сейчас text search/research имеют
   более узкие форматы, чем extract_material. Объедини доступное представление в пределах
   текущих инструментов: никаких выдуманных цитат, молчаливой обрезки или заявления о полном
   чтении по одной странице. Большой источник требует явного отбора/границ, а не скрытого reject.
6. search_assets пока даёт ссылки, не вставляет изображение. Либо доведи selected asset→
   authorised download→validated media→slot→revision/export с существующей защитой URL и медиа,
   либо оставь честный discovery-only сценарий и укажи незакрытый feature. Не обещай вставку
   в ответе ассистента без фактической операции. Полноценное ИИ-редактирование диаграмм/таблиц
   и vision-inspection сохранённой правки также требуют реального end-to-end пути, metadata
   preview не являются визуальным анализом. Не строй второй редактор.
   Отдельный подтверждённый разрыв: read_deck и read_audit в chat-tools.ts ещё читают исходные
   plan.json/final-review, тогда как preview_slide/check_slide_fit/check_content_coverage уже
   используют server snapshot. Подключи read_deck к той же revision/hash модели; исходный аудит
   маркируй original/stale, пока не проведён свежий. Проверка: правка текста→save→новый chat turn
   читает новый текст, не выдаёт старый аудит за аудит правки; конфликт revision явный.
7. Собери один acceptance report на одном SHA: 5/10/15 слайдов; два характерных и один
   незнакомый шаблон; богатые/скудные материалы; числовые данные с 0/null/отрицанием;
   три отличимых варианта; PPTX/PDF открываются; правка→новая сессия→export той же revision;
   доступ другого аккаунта запрещён. Не нужна бессмысленная полная декартова матрица.
8. Измеряй от принятой команды generation на подготовленных входах до durable completion
   всех экспортов. Не увеличивать 290-секундный budget или concurrency. Подготовка видима
   отдельно. Цели: максимум 300 секунд, целевой p95≤240; публикуй p50/p95/p99/worst, число
   наблюдений и метод, first success/auto recovery/resume, 429 и queue/network/model/engine time.
   Failed/slow не исключать ради цифр. Из одного запуска p95 не выводить. Большие live нагрузки
   не делать без отдельного бюджета. Офлайн fault tests выполняются без платной сети.

## Исполнение

Можно до двух субагентов одновременно на крупные независимые зоны (runtime fault/ledger и
materials/tools), без рекурсии, микропоручений и повторного аудита всего проекта. Простые
тесты и документацию — дешёвой модели при наличии. Сам интегрируй и ревьюй. Если работа
пересекается с незавершённым PR, согласуй конкретный файл/контракт один раз, не дублируй пакет.

Только yarn/uv и Nx. Все LLM вызовы в TS, PPTX в Python, engine слои независимы. Zod/codegen
вместе, registry semver, никаких отключённых проверок, шаблонного hardcode, секретов/runs/
датасета организаторов в Git. Не меняй модель или платный ключ без согласия владельца.

Результат: рабочий PR, воспроизводимые тесты/скрипты, таблица требований со статусами
implemented/verified/blocked и конкретной причиной, сравнение логических задач/HTTP/токенов
на одинаковых входах, архив разрешённых артефактов с revision/hash и честный список release
gates. Live/production проверки без доступа и бюджета пометь неподтверждёнными; заверши все
независимые офлайн задачи. Не закрывай весь UltraReview по наличию таймера или успешному build.
