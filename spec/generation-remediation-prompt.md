4. Оптимизировать на уровне обращений к модели, контекста, инструментов, алгоритма, представления содержания и работы с результатами.

6. Надёжность со стороны нашего сервиса должна приблизиться к 100% на поддерживаемых корректных входах: готовая работа не теряется, внутренние ошибки не заставляют повторно оплачивать её, единичная восстанавливаемая ошибка не уничтожает всю сборку.
7. Качество должно быть высоким во всех трёх вариантах. Нельзя экономить молчаливой потерей фактов, уменьшением читаемости, отключением аудита или выдачей черновика как успешной колоды.
8. **Три варианта должны быть действительно разные.** Небольшие изменения кегля, плотности, переносов, полей или перестановка пары блоков не удовлетворяют запросу.
9. Экономия не должна достигаться за счёт трёх почти одинаковых презентаций. Разная композиция и визуальная концепция обязательны, но общие факты не нужно дорого сочинять заново три раза.
10. На стадии подготовки этого задания пользователь запретил реализацию. Не перепутай будущий implementation scope с разрешением выполнить его сейчас.

## 5. Установленные дефекты и места исследования

Номера строк относятся к диагностическому снимку и могут сместиться. Используй имена символов и актуальную реализацию.

### 5.1. Wall-clock ограничивает остановку, а не гарантирует результат

- `apps/api/src/generation/build-budget.ts`: `BUILD_DEADLINE_MS=290_000`.
- `packages/pipeline/src/generation/runner.ts`: plan/write → до трёх audit/repair проходов → export/render.
- Общий composition plan в рамках одного build есть, но содержание каждого варианта пишется отдельно.
- Для 10 слайдов и 3 вариантов получается 30 базовых writer-задач плюс rewriter/critic/HTTP retries.
- Фактическое production `MODEL_MAX_CONCURRENCY=3`, хотя default в некоторых исходниках/локальном Compose — 8.
- На один variant workflow настроено несколько workers; это не увеличивает фактическую провайдерскую квоту.
- Общий limiter разделяется с другими модельными обращениями. Наличие трёх HTTP slots само по себе не предотвращает RPM/TPM ограничения.
- Резерв на export около ожидания картинок не является полным end-to-end stage budget.

### 5.2. Дорогая модель и reasoning размножаются по задачам

`model-plan.json` во всех исследованных runs:

- writer: личное подключение, `gpt-5.6-terra`;
- rewriter: тот же writer-fallback;
- planner и critic: тот же writer-fallback;
- thinking=true, reasoningEffort=medium;
- vision: server `qwen38-27b-fp8`, до финального visual review эти прогоны не дошли.

`apps/api/src/generation/generation.service.ts` разрешает роли и передаёт одни thinking/reasoning настройки всем текстовым провайдерам. Отдельной независимой роли rewriter в этом пути нет.

`packages/pipeline/src/generation/provider.ts`:

- thinking добавляет до 8192 токенов к допустимому output budget; это максимум, а не измеренное потребление;
- при обрезанном/невалидном ответе возможны повторы с растущим лимитом;
- `AttemptBudget(110)` — ограничитель дополнительных retries, не общего числа вызовов, токенов или долларов;
- учитываются преимущественно успешно валидированные ответы, не все потенциально оплаченные попытки.

`packages/pipeline/src/generation/workflow.ts`:

- каждый вариант вызывает writer отдельно;
- есть локальные циклы correction;
- `rewriteSlide` может сделать до пяти логических обращений;
- запрашиваются по три альтернативы для слотов;
- provider имеет собственный retry слой;
- после этого возможны ещё общеколодные audit/repair циклы.

В сохранившемся хвосте первой попытки есть 14 завершённых rewriter activities, третьей — 10. Это нижние границы: UI сохраняет максимум 32 activity и вытесняет старые. Не используй эти числа как полный HTTP call count или billing.

### 5.3. Chat retry не использует execution checkpoint

`apps/api/src/chats/chat-tools.ts`, runBuild/build_deck:

- `retry:true` разрешает новый запуск после terminal failure;
- создаётся новый BuildPart;
- вызывается `generation.start(generationInput, scope.account, undefined, onActivity)` либо обычный start;
- предыдущий execution plan, готовые слайды и workflow snapshot не передаются;
- одобренный chat planId ошибочно воспринимается пользователем как полноценная память выполнения;
- `generationBrief(...)` заново собирается из истории: даже сообщения «продолжить» изменяют вход.

Размеры brief четырёх попыток: 3827, 3948, 4069, 4220 символов. Хеши composition-plan одинаковы внутри тройки одного build и разные между всеми четырьмя builds. На каждом повторе снова тратилось около полутора минут до записи plan.

`GenerationService.retryVariant()` в `apps/api/src/generation/generation.service.ts` читает старые request/composition-plan и повторяет один variant без planner, но chat его не вызывает. Даже этот endpoint не продолжает с точной последней успешной slide task.

Mastra SQLite snapshots существуют; runner всё равно создаёт новый workflow через createRun().start(). Наличие mastra.db не доказывает подключённый resume. `plan.json` записывается поздно, после critic, а не сразу после каждого готового слайда.

### 5.4. Учёт usage теряется на реальном API-пути

`runner.ts` формирует modelCalls через `instanceof OpenAICompatibleProvider`. API передаёт `RoutedTextProvider`, который не наследует этот класс. Поэтому modelCalls на этом пути может быть пустым даже при success.

При failure сохраняется преимущественно message/elapsedMs. В проверенной Mastra SQLite не было ai spans. Полного durable журнала HTTP attempts, reasoning/cached usage и расходов не было.

Не выдумывай точный тариф alias `gpt-5.6-terra`, число токенов, число HTTP sends и расклад $3 по стадиям.

### 5.5. Ошибки объединяются в неправильные категории

`runner.ts`: любой aborted signal классифицируется как budget-exceeded и retryable=true, включая browser cancel.

Текст `Build deadline passed before the run could start` возникает и после почти пяти минут настоящей работы, когда следующий шаг встречает исчерпанный общий budget. Такой текст вводит пользователя в заблуждение.

В интерфейсе остаётся общая ошибка или `The call was cut off`, без реального объяснения оплаченной/сохранённой работы.

### 5.6. Template readiness неполная

В profile шаблона есть generation profile, но смысловой index отсутствует. Логи: `The template indexer described no composition`.

Индексация best-effort, ошибка не блокирует generation и не объясняется пользователю как degraded readiness. Вклад в время/стоимость отдельно не измерен.

### 5.7. Исходные тесты не ловят продуктовые дефекты

На диагностическом снимке прошли 3153 product tests, 9 optional tests были skipped; отдельно прошли 10 evidence-checks. API/pipeline typecheck/lint и Python lint прошли.

Это исторический baseline, не утверждение о текущей ветке. Зелёные unit tests не доказали реальную готовность трёх качественных вариантов до 300 секунд, стоимость, resume и визуальную различимость. Нужны новые acceptance/fault/quality проверки.

## 6. Что нельзя считать исправлением

Не принимать ни один из следующих обходов:

- увеличение 290-секундного deadline, request timeout, HTTP slots, числа реплик или числа параллельных API keys для обхода квоты;
- увеличение retries или более агрессивные повторные запросы после 429;
- три независимых дорогих полных генерации «ради различий»;
- один дизайн, клонированный трижды с косметическими изменениями;
- удаление обязательных фактов, источников, выводов, speaker notes или пользовательских ограничений;
- превращение проблем качества в warning только ради зелёного статуса;
- отключение контекстного/детерминированного аудита без равноценной доказанной замены;
- рендер всей страницы картинкой вместо native editable PPTX;
- выдача старых, demo, пустых или промежуточных артефактов как новых готовых;
- скрытый переход на другую модель/ключ/платный аккаунт;
- перенос реальной генерации до старта таймера с переименованием её в подготовку;
- restart workflow с нуля под названием resume;
- тестирование только со сверхбыстрым fake provider без медленных ответов, 429 и реального рендера;
- обещания «идеально, 100%, $0.10» без определения условий и измерений.

Допустимо исправить существующую настройку, которая ошибочно превышает квоту, но не наращивать provider pressure. Основное улучшение обязано происходить за счёт меньшей полезной работы модели, устранения повторов и качественной детерминированной обработки.

## 7. Целевая архитектура: общий смысл, три самостоятельных дизайна

Это направление решения, а не требование использовать именно такие имена сущностей. Проверь совместимость с существующим DeckPlan/CompositionPlan/SlideIR и минимизируй миграции.

### 7.1. Immutable GenerationSpec вместо повторной сборки истории

При подтверждении generation request сформируй нормализованный snapshot:

- одобренная revision плана;
- аудитория, цель, длительность/объём, обязательные тезисы;
- факты, evidence/source references и разрешённые визуальные данные;
- template hash/capabilities/fonts;
- выбранные модельные роли и permissions;
- точные semantic constraints, seed и версии.

«Продолжить», «повтори» и транспортные события не должны менять этот snapshot. Изменение содержания — явная новая revision с понятной инвалидизацией зависимых результатов.

### 7.2. Общий ContentPlan/EvidenceGraph

Раздели:

- что обязано быть сказано и чем подтверждено;
- как это сформулировано для нескольких допустимых ёмкостей;
- как это визуально раскрыто в каждом из трёх вариантов.

Общие факты, смысловая структура и обязательные тезисы создаются/проверяются один раз. Не требуй одинакового текста слово в слово в каждом варианте: это мешает настоящей визуальной адаптации. Требуй семантические инварианты: сохранённые утверждения, оговорки, числа, источники, пользовательский intent и границы доказанности.

Если outline уже одобрен человеком, не запускай заново дорогой narrative planner. Различай согласование истории и техническое назначение макетов. Максимум работы компилируй детерминированно из уже известного.

Фразы короткой/средней/расширенной длины создавать только там, где есть реальная потребность. Не раздувай каждый запрос тремя ненужными версиями всех полей, чтобы формально назвать это оптимизацией.

### 7.3. Три VariantDesignPlan, а не три плотности

Спроектируй три заметно разные глобальные визуальные стратегии, производные от допустимых возможностей конкретного шаблона:

- разные композиционные последовательности, доминирующие типы компоновки и визуальная иерархия;
- разное раскрытие смысла: например, редакционный тезис/аргумент, визуальная история/процесс, сравнение/аналитическая схема — это примеры, не зашитые три типа для всех входов;
- разное распределение текстовых, табличных, диаграммных, иллюстративных и акцентных представлений там, где это оправдано данными;
- собственная ритмика, тип cover/closing, способы сравнения/выделения выводов;
- единый бренд и корректность относительно исходного шаблона.

Крупные различия не должны требовать выдуманных чисел, неподтверждённых диаграмм, новых фактов или нарушения утверждённого плана. Не менять согласованные порядок, количество и смысл слайдов без разрешения пользователя. Внутри этих ограничений визуальная вариативность должна быть существенной.

Не своди разнообразие к цветовым темам, если шаблон не разрешает новые цвета. Не меняй брендовые шрифты и не придумывай координаты под один шаблон. Допустимые трансформации компонентов и композиционные комбинации выводи из профиля и проверяй движком.

Если шаблон объективно имеет ограниченные возможности, сначала исследуй общие допустимые преобразования и комбинации. Если три честно разных качественных варианта невозможны в рамках обязательных ограничений, выяви это на readiness этапе до расходов и объясни ограничение; не выдавай клоны за три концепции. Этот edge case не заменяет реализацию для нормальных разнообразных шаблонов.

### 7.4. Качественная детерминированная адаптация

- Общие смысловые единицы сопоставляются с подходящими композициями по реальной ёмкости, ролям блоков и evidence.
- Engine измеряет текст с реальными шрифтами и размерами, без молчаливого fallback.
- Модель не нужна для нумерации, дат, идентификаторов, проверок длины, поиска дублирования по точным признакам, маршрутизации и простых технических преобразований.
- Для проблемного поля выбирать уже валидную смыслосохраняющую формулировку, затем другую допустимую композицию; targeted rewrite — только когда детерминированные возможности исчерпаны.
- Нельзя «исправлять» переполнение обрезкой строки, многоточием вместо обязательного тезиса или произвольным уменьшением шрифта.
- Детерминированный fallback должен быть полноценной редактируемой версткой известных фактов, не заглушкой. Его качество и разнообразие тоже проходят gate.
- Каждая адаптация имеет provenance и зависит от конкретной revision содержания.

## 8. Экономика модельных запросов и инструментов

Сначала составь фактический call graph: trigger → role/tool → input → expected output → retries → dependencies. Отдельно посчитай логические tasks, реальные HTTP sends и токены; это разные метрики.

Сравни не менее двух реалистичных схем распределения модельной работы:

- единый большой ответ на deck;
- небольшое число ограниченных смысловых батчей + общая проверка + targeted adaptations.

Выбери по измеренным latency, output reliability, reusable results, token cost и blast radius. Не заменяй 30 маленьких запросов одним гигантским, который полторы минуты рассуждает, обрывается по output limit и заставляет переплачивать за всё.

Обязательные направления:

1. Сократить реально отправляемые токены: релевантный компактный каталог, ссылки на evidence, только нужные slot constraints. Не слать весь template profile в каждый запрос.
2. Убрать повторение одного и того же огромного schema/instruction там, где provider protocol позволяет надёжный более компактный контракт. Не ослаблять runtime validation.
3. Переиспользовать результаты подготовки и модели по полному dependency key; не создавать paid calls при обычном чтении UI.
4. Формировать задания сразу с измеренными вместимостями и обязательными смысловыми элементами, чтобы сокращать число repair passes.
5. Ограничить инструментальную петлю графом допустимых переходов и budget. Не позволять chat assistant бесконечно решать, «не вызвать ли build ещё раз».
6. Для каждого LLM role обосновать необходимость, модель, reasoning, input/output cap и условия вызова. Перенос thinking пользователя на каждую микроправку без объяснения недопустим.
7. Не менять явно заданное пользователем поведение модели тайно: отделить настройки чата от generation policy и показать effective role configuration.
8. Переиспользовать общий semantic audit; отдельно проверять variant-specific фактическое отображение и полноту. Один общий critic не заменяет проверку каждого конечного файла.
9. Адаптивно группировать независимые мелкие операции только если это уменьшает tokens/requests и не приводит к большим повторным потерям при сбое.
10. Считать первичные вызовы вместе с retries, compatibility negotiations, probes, image generation, vision и tool-driven calls. Никаких «бесплатных» незаметных служебных запросов.

Не задавай произвольное минимальное число вызовов как самоцель. Обоснуй плановый и максимальный HTTP/token budget на 10 слайдов и на поддерживаемый диапазон. Потребление должно быть существенно ниже исходного при не худшем качестве; результат подтверждается измерениями, а не одной выбранной дешёвой моделью.

## 9. 429, квоты и end-to-end deadline

Сохрани существующий потолок concurrency и не повышай его. Исследуй квоту как минимум по concurrent requests, RPM и TPM, включая общий аккаунт/endpoint и другие задачи сервиса. Лимит может быть общим между разными model IDs/подключениями; не считай новый connectionId новой квотой без доказательств.

Сделай единый прозрачный scheduler/provider boundary:

- дедупликация одинаковых задач;
- квотно-осознанное планирование и bounded waiting;
- priority/fairness, чтобы чат и соседняя сборка не вытесняли обязательный финальный экспорт;
- Retry-After и backoff с jitter без retry storm;
- никакого немедленного повторения 429 через другой слой;
- одна общая retry policy вместо перемножения provider/workflow/tool/agent retries;
- запрет выдачи новой задачи, если она не помещается в remaining time/request/token/cost budget;
- отмена очереди без отмены уже проверенных результатов.

Раздели queue delay, network/server time, token generation и engine/render time. Не объявляй, что модель «работала 50 секунд», если большая часть ушла на очередь нашего limiter.

### Временные цели

- Обязательный внешний результат: все три варианта и обязательные артефакты готовы не позднее **300 секунд** от принятой пользовательской команды generation на подготовленных входах.
- Внутренняя целевая скорость: **p95 не более 240 секунд**, чтобы оставался реальный запас. Это новый целевой gate, не уже измеренный факт.
- Существующий основной budget около **290 секунд не увеличивать**. Измеряй весь пользовательский путь: локальный 290-секундный таймер не разрешает добавить перед ним ещё минуту скрытой генерации.
- p99, worst observed, доля успеха, 429 count и фактический запас времени публикуются отдельно.
- Не сбрасывай clock при stage retry или тихом пересоздании build. Дополнительное время при явном возобновлении после остановки показывается отдельно вместе с cumulative elapsed/cost; это не делает первую попытку прошедшей SLA.

Вычисли stage budgets из измерений: plan/content/design/adaptation/audit/export/render/persistence. Обязательно резервируй обязательный export/render и финальную публикацию всех трёх вариантов до запуска дорогих исправлений. Приоритизируй критические дефекты, не трать последние секунды на чисто вкусовой critic loop.

Подготовка шаблона/материалов допустима отдельно по спецификации: это явный readiness этап с индикатором, кешем и понятной ошибкой. Нельзя называть написание финального содержания подготовкой, чтобы скрыть SLA breach.

Невозможно обеспечить готовый качественный результат за 300 секунд при бесконечно недоступном upstream. Опиши честный supported envelope по размеру/сложности входа, latency и квотам; до расходов выявляй неподходящую конфигурацию. Не урезай молча поддерживаемый сценарий до одного простого слайда и не объявляй его победой над исходной задачей.

## 10. Настоящее восстановление и жизненный цикл

Нужна единая семантика для chat/UI/API/CLI, где они используют общий pipeline:

- `start`: новая согласованная generation revision;
- `resume`: продолжить ту же revision по валидным checkpoints;
- `retry failed task/variant`: повторить минимальный неуспешный участок;
- `regenerate`: намеренно пересоздать выбранный участок/всё, с объяснением расходов;
- `cancel`: прекратить работу, сохранить уже полученное;
- `reconcile`: выяснить исход неоднозначного внешнего запроса без слепого дублирования.

Раздели стабильный buildId, variantId, taskId и attemptId. Chat BuildPart и backend build не должны иметь несогласованные идентификаторы без явной связки.

Checkpoint каждой переиспользуемой задачи:

- normalized input/dependency hashes, `contentHash`, generation/plan revision;
- template hash, schema/prompt/agent versions;
- effective model/capability policy, seed, варианты дизайна и значения параметров, влияющих на результат;
- валидированный output и references на артефакты;
- task state, timestamps, last successful boundary;
- usage/cost linkage и применённые исправления.

Сохраняй checkpoint сразу после успешной проверки результата, а не после всей колоды или ответа critic. Обеспечь атомарную запись файлов/метаданных или явное crash-safe восстановление orphan records. Не считай результат завершённым до durable commit.

Проверь, что исходное хранилище действительно умеет восстановить нужный шаг. Если Mastra snapshots достаточно — корректно подключи существующий run/restart API и schema compatibility. Если нет — добавь минимальный собственный слой задач/checkpoints поверх текущих PostgreSQL/filesystem. Не строй крупную распределённую инфраструктуру без необходимости.

Конкурентность и отказы:

- idempotency ключ для start/resume и каждой side-effect задачи;
- lease/fencing от устаревших workers и callbacks;
- согласование двух одновременных resume запросов;
- восстановление после crash между ответом provider и сохранением, между file write и DB commit, во время export/publication;
- состояние unknown для неоднозначно завершившегося внешнего вызова;
- старый attempt не перезаписывает новый и не отменяет чужую revision;
- все references проверяются по owner/account; resume не открывает чужие данные;
- частичная инвалидизация: изменение одного поля не требует повторной генерации независимых готовых слайдов.

Не обещай exactly-once оплату там, где у provider нет idempotency/status retrieval. Если response потерян после биллинга, объясняй эту границу, сохраняй request ID и выполняй reconciliation, если protocol позволяет. Не приравнивай неизвестный исход к нулевой стоимости.

При перезапуске API не превращай все running builds безусловно в failed с единственным советом начать заново. Нужен проверенный recover/reconcile путь. Явно отменённые пользователем задачи автоматически не возобновлять.

Старые runs нельзя объявлять возобновляемыми без совместимого state. Опиши безопасную миграцию/legacy adapter и возможность извлечь валидные результаты без новых расходов; где данные реально отсутствуют — честно указать минимальный объём повторной работы.

## 11. Стоимость: durable ledger и бюджет всей сборки

Реализуй provider-independent observability, которая не зависит от конкретного `instanceof` и учитывает RoutedTextProvider, vision, images и compatibility layer.

На каждую реальную HTTP-попытку append-only запись:

- build/revision/variant/task/attempt/role;
- provider connection identity без секрета, effective model, provider request ID;
- input hash, причины вызова и retry;
- enqueue/start/end timestamps, queue/network/model durations;
- HTTP status, finish reason, outcome, cancellation reason;
- input/output, cached и reasoning tokens, если provider сообщает; отсутствующие поля — unknown;
- tariff source/version, currency, estimate/actual/unknown, charge reconciliation;
- checkpoint/artifact linkage.

Записывай факт попытки до отправки; outcome/usage — до parsing/schema acceptance, чтобы не терять цену невалидных ответов. Формат не должен хранить API key или полный prompt в обычных логах.

Денежный бюджет:

- один budget на build/revision с накоплением attempts/resume, а не новый бесплатный счётчик при каждом повторе;
- резервирование стоимости in-flight запросов и освобождение/сверка резерва;
- atomic check-and-reserve между параллельными задачами;
- контролируемый max output/repair budget с учётом фактической модели;
- неизвестная стоимость не равна нулю и не позволяет бесконечные sends;
- бюджет не считается точной гарантией внешнего счёта при неизвестном тарифе/биллинге; показаны остаточная неопределённость и политика безопасной остановки;
- пользователь видит оценку до старта, текущий расход/неопределённость и объём возможной доплаты при regenerate.

Сопоставь baseline и новый pipeline на одинаковых входах и согласованном provider/model policy. Раздельно покажи эффект алгоритма, выбора модели и reasoning. Не выдавай экономию от неподтверждённого более дешёвого endpoint за архитектурное улучшение.

## 12. Качество: формализовать «идеально», не заменить его галочкой

Составь измеримую рубрику:

1. Факты: нет выдуманных чисел/дат/источников; доказательства соответствуют утверждениям; сохранены оговорки и неопределённость.
2. Содержание: все обязательные тезисы/ограничения пользователя покрыты, есть цель и связный вывод, нет бессмысленных повторов и пустых полей.
3. Дизайн: ясная иерархия, читаемость, выравнивание, визуальный баланс, осмысленная графика, сохранён бренд шаблона.
4. Верстка: нет переполнений, обрезанных слов, наложений, broken images, неверных форматов чисел, тихой подмены шрифтов.
5. Разнообразие: три самостоятельные концепции, не косметические clones.
6. Артефакты: все форматы соответствуют одной окончательной audited revision, PPTX редактируемый; нет placeholder/mock результата.

Выдели hard blockers и мягкие эстетические замечания. Осмысленное завершение без вкусового polishing допустимо только при прохождении обязательных gates; слово «warning» не должно оправдывать фактическую ошибку или нечитаемый слайд.

### Проверка разнообразия

Введи pairwise structural signatures для трёх вариантов: последовательности composition families, расположение и роли блоков, визуальные представления, иерархия/ритм. Не ограничивайся сравнением ID макетов: разные ID могут давать одну картинку.

Добавь visual comparison конечных рендеров и общий contact sheet всех вариантов. Порог различимости обоснуй на репрезентативных примерах; не подгоняй его под одну колоду. Нельзя пройти gate случайным шумом, переменой цвета или перестановкой незначимых объектов.

Проведи человечески интерпретируемое сравнение: чем концептуально отличается каждый вариант и почему это оправдано содержанием. Где необходимо слепое визуальное сравнение — не подменяй его самопохвалой модели. Если baseline не экспортируется, используй last-good колоды/согласованный reference corpus, не выдумывай сравнение с несуществующим файлом.

Смысловой critic не является математическим доказательством правды. Дополняй source provenance, детерминированными проверками чисел/цитат/coverage и выборочной визуальной оценкой; не умножай дорогое «модель проверяет модель» без измеримой пользы.

## 13. Шаблоны, изображения и обязательные экспорты

- Устрани причину некорректного/пустого template index и отсутствие явного readiness state.
- Кешировать по template/profile/indexer/schema/model dependencies; unsuccessful preparation тоже должна иметь bounded retry/backoff, а не платно повторяться при просмотре.
- Модельный индекс должен добавлять смысл, а не заменять достоверную геометрию парсера.
- Не копировать текст примера шаблона как факты пользователя и не считать декоративный блок обязательным пользовательским содержанием.
- Изображения/QR/диаграммы/таблицы получают общий asset cache там, где смысл одинаков; визуальные концепции могут использовать asset по-разному.
- Не генерировать три одинаковые платные картинки только из-за разных variant directories.
- Нельзя обещать изображения/поддержку неизвестного image model, не проверив capabilities.
- Все обязательные существующие форматы должны отражать один финальный edited/audited state: native PPTX, PDF, HTML, previews и PNG ZIP там, где продукт уже их предлагает.
- Не оставляй demo/null URLs. Проверяй реально скачанные файлы, page/slide count и hashes/revision linkage.
- Если export/render падает, повторяется только нужный детерминированный этап; модельные задачи и два успешных варианта не выполняются заново.
- Готовые варианты сохраняются и доступны при сбое третьего, но partial success не объявляется выполнением требования всех трёх.
- Нельзя выдать устаревший audit за аудит файла после поздней правки.

## 14. Ошибки и UX

Различать как минимум:

- user-cancelled;
- build-deadline-exceeded;
- provider-rate-limit;
- provider-timeout;
- provider-auth/quota-unavailable;
- provider-invalid-response;
- preparation-not-ready;
- content-fit/quality-blocked;
- engine/export/render-failed;
- persistence-failed;
- unknown-external-outcome.

Коды, retryability и разрешённые действия должны отражать реальный исход. HTTP 403, отсутствие квоты, критическая ошибка источников и отмена пользователем не лечатся автоматическим стартом всей колоды.

Интерфейс показывает:

- фактический этап и проверяемый прогресс без выдуманных процентов;
- уже сохранённые результаты и оставшуюся работу;
- понятную причину остановки;
- cumulative время/расход и оговорку об unknown usage;
- отдельно «Продолжить недоделанное», «Пересоздать вариант» и «Начать заново» с ценой/объёмом повторной работы.

Закрытие вкладки/потеря SSE сами по себе не должны отменять серверную сборку. Явная Stop отменяет выдачу новых задач и сохраняет уже выполненное. Проверь фактические причины browser `/cancel`, чтобы unintended UI lifecycle не убивал generation.

Смена вкладки, reconnect, повтор tool call, одинаковый request ID и повторная доставка события не создают второй платный build.

## 15. Работа с тестами — сначала RED, потом GREEN

До реализации зафиксируй 5–10 ключевых failing regression tests в соответствии с правилами репозитория; затем расширяй покрытие. Не оставляй новую задачу без теста только потому, что существующие тысячи тестов зелёные.

Минимальные первые 10 сценариев:

1. Три содержательно полных, визуально разных варианта на 10 слайдов при прежнем concurrency; плановый request/token budget существенно меньше baseline, без скрытого повторения всей истории.
2. Сбой после сохранения слайда №7: resume не вызывает planner и не оплачивает заново валидные слайды №1–7.
3. Один failed variant/export: два готовых не генерируются и не оплачиваются заново, повторяется минимальная задача.
4. Дублированные start/resume/request IDs и два одновременных resume: один исполнитель/результат, работают ownership и fencing.
5. Crash на границах provider response/checkpoint/file/DB/publication: нет ложного done, потери подтверждённых задач и затирания новой revision старым callback.
6. Серия 429 с Retry-After/RPM/TPM ограничением: нет retry storm, quota bypass и роста concurrency; сохраняются время на экспорт и причина остановки.
7. Truncated/invalid/schema-incompatible ответ: все attempts отражены в ledger, bounded retry, валидные независимые задачи сохранены.
8. Cancel и потеря SSE различаются: browser disconnect не отменяет build, Stop не классифицируется как deadline и не вызывает автопродолжение.
9. In-flight денежные резервы и накопление attempts: бюджет не обнуляется на resume, unknown usage виден, shared ledger работает для routed/vision/images.
10. Профиль/источник/план/промпт изменились: корректная частичная инвалидизация; сохранены семантические инварианты и source evidence во всех трёх конечных файлах.

Дополнительная матрица:

- одна колода, две одновременно, соседний чат, исчерпанный общий TPM;
- один незнакомый шаблон, несколько композиционно разных шаблонов, повторяющиеся/бедные шаблоны;
- мало и много текста, длинные русские слова, Unicode, таблицы/графики, числа с оговорками, PDF/HTML источники;
- неподдержанный/пустой template index, шрифт отсутствует, damaged input;
- provider 400/401/403/429/5xx, network drop, потерянный response после возможного биллинга;
- engine/export timeout, отменённый subprocess, corrupt artifact;
- рестарт API и восстановление старого совместимого checkpoint после deployment;
- ACL/ownership, отсутствие секретов в ledger, миграции старых runs;
- попарное разнообразие, все обязательные тезисы, соответствие окончательных экспортов editor state.

Используй fake provider с управляемыми delays/usage/status, fake clock и deterministic fault injection для частых тестов. Таймеры должны проверять настоящую логику очередей/резервов, а не только магический быстрый happy path. Записанные ответы не должны зависеть от конкретного production шаблона.

Все новые audit checks — passing/failing fixtures. Контракты проверять общими Zod/Pydantic fixtures. Проверяй broken imports, typecheck, lint/PEP8, boundaries, codegen diff, сборку и существующие тесты.

## 16. Измерения, надёжность и критерии выпуска

Разделяй уровни evidence:

1. Static/source: почему код теперь устроен правильно.
2. Unit/integration/fault tests: какие сценарии доказаны без реального provider.
3. Локальный runtime: настоящий API + engine + persistence + export.
4. Browser E2E: start/error/resume/reconnect/download и фактический пользовательский путь.
5. Live provider: согласованные по бюджету вызовы, измеренные latency/usage/429.
6. Production: только после отдельного разрешения deploy и последующих проверок.

Build success не равен generation success; HTTP 200/healthy не равен качественной колоде; один удачный live run не равен SLA.

Для supported envelope веди таблицу:

- template/input class, slides, user model policy, roles/reasoning;
- generation start и durable completion всех вариантов/экспортов;
- p50/p95/p99, worst observed и оставшийся резерв;
- first-attempt success, automatic recovery, explicit resume success;
- internal failures отдельно от provider outages, но публикуй и end-to-end итог;
- logical tasks, HTTP sends, retry reasons, 429 count, input/output/cached/reasoning tokens;
- стоимость/unknown charges, cumulative стоимость resume;
- deterministic/semantic/visual findings;
- diversity metrics и contact sheets;
- скачанные артефакты с revision/hash.

Не исключай failed/slow runs из статистики только чтобы получить красивый p95. Поддерживаемый входной диапазон и критерии исключений определяются до измерений.

«Почти 100% со стороны сервиса» формализуй как отсутствие предотвратимой потери state/дублирования/ложного done и высокий SLO успешного завершения при оговорённых внешних условиях. Не обещай абсолютные 100% и не ссылайся на внешнего провайдера вместо исправления собственных дефектов.

Оцени статистическую уверенность. Пример: 10 успешных live запусков ещё не доказывают 99% надёжности. При нуле отказов приблизительная 95%-граница сверху на долю отказов равна 3/n; около 300 независимых репрезентативных запусков нужны, чтобы обосновывать примерно 1% этой границей. Это пояснение планирования evidence, не разрешение потратить деньги на 300 прогонов. Большую часть отказоустойчивости доказывай дешёвыми fault tests, live sample согласуй отдельно и обозначай ограничения его статистики.

Release gate:

- ни один ранее подтверждённый checkpoint не теряется на поддерживаемых сбоях;
- resume действительно продолжает, regenerate явно отличается;
- three variants complete <=300 секунд на согласованном test envelope, целевой p95 <=240 секунд;
- concurrency и квотная нагрузка не увеличены, request/token efficiency измеримо лучше;
- нет критических quality findings и ложных success;
- три варианта проходят структурный и визуальный diversity gate;
- все обязательные артефакты настоящие, доступны и согласованы с финальной revision;
- cost ledger и limits работают при успехе, ошибке, отмене и неоднозначном исходе;
- тесты, сборка, lint/types/boundaries/codegen проходят;
- remaining gaps явно перечислены, а неподтверждённый live/deploy gate не объявлен закрытым.

## 17. Рекомендуемый порядок будущей реализации

### Этап A. Recon и рабочая спецификация

Прочти весь relevant path, проверь состояние repo и защищай чужие изменения. Построй карту call graph, state machine и источник каждого лишнего paid request. Обнови рабочую спецификацию с новыми требованиями действительно разных вариантов и запретом роста нагрузки.

До кода представь краткую архитектурную записку: проблема → extension point → минимальное изменение → риск → тест. Выдели backward compatibility и миграцию старых state.

### Этап B. RED-тесты, наблюдаемость и budgets

Добавь первые regression tests. Введи durable attempt ledger и единую модель time/request/token/cost budgets. Устрани слепоту routed usage и смешение cancellation reasons. Не объявляй это окончательным исправлением скорости.

### Этап C. State и настоящий resume

Нормализованный GenerationSpec, совместимые checkpoints, idempotency, lease/fencing, минимальная инвалидизация, recover/reconcile. Объедини chat/UI/backend semantics. Докажи fault tests до перехода к дорогому generation redesign.

### Этап D. Устранение повторного сочинения и настоящие варианты

Общий semantic content, compact/batched model tasks, три глобальных design plans, engine-driven composition и targeted adaptation. Сократи контекст и cascaded repairs. Не откладывай разнообразие как косметическую задачу после performance — оно часть архитектуры.

### Этап E. Quality/readiness и end-to-end runtime

Template index/readiness, semantic/visual gates, export consistency, cache assets, budget-aware recovery. Проверь неизвестные шаблоны и реальный editable output.

### Этап F. Измерения и подготовка релиза

Локальные/браузерные evidence, согласованные live sample, сравнение baseline/new по времени/стоимости/качеству/различимости. Подготовь миграции и безопасный rollout/rollback, не выполняя production actions без отдельного разрешения.

Это порядок зависимостей, а не право бесконечно откладывать implementation. После разрешения локальной реализации доведи согласованный scope до рабочего проверенного результата; при внешнем блокере продолжай независимые локальные этапы и чётко разделяй done/blocked/unverified.
